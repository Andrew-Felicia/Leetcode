给我讲讲你设计的大模型后训练流程：对齐数据怎么构造？奖励建模如何评测？在线/离线评测各怎么做？


我设计的大模型后训练不是“一次 SFT + 一次 RL”，而是一个以评测为中心的闭环：

```text
定义行为规范与评测集
        ↓
构造 SFT / 偏好 / 安全 / 可验证任务数据
        ↓
SFT 冷启动
        ↓
偏好优化：DPO，或 RM + PPO/GRPO
        ↓
离线能力、安全、系统评测
        ↓
灰度发布与在线 A/B
        ↓
失败样本聚类、重新标注、下一轮训练
```

关键原则是：先定义“什么算好”，再训练奖励模型，否则很容易只把代理奖励做高，却没有提升真实用户体验。

## 1. 先定义对齐目标

我不会直接把“有帮助”压缩成一个模糊标签，而是拆成多个维度：

- 正确性：事实、推理、计算是否正确。
- 指令遵循：格式、语言、长度、约束是否满足。
- 有用性：是否真正解决任务，而不是泛泛而谈。
- 诚实性：不确定时能否表达不确定，不伪造引用。
- 安全性：危险请求的识别、拒绝边界和安全替代方案。
- 风格：简洁程度、结构、语气、是否过度迎合。
- Agent 能力：工具选择、参数、执行结果利用、恢复能力。
- 系统指标：延迟、成本、输出长度、工具调用次数。

其中安全通常是硬约束，有用性和风格是软目标。不能让“更有帮助”的平均得分抵消严重安全退化。

随后建立 prompt taxonomy：

```text
任务类型 × 难度 × 语言 × 长度 × 风险级别 × 是否调用工具
```

训练集、开发集和评测集按 prompt 来源、用户、时间和语义簇切分，不能只是随机按行切分，否则近重复 prompt 会造成数据泄漏。

## 2. 对齐数据怎么构造

### 2.1 SFT 数据

SFT 主要负责建立基本行为模式和输出格式。数据来源包括：

- 经过授权和脱敏的真实任务。
- 专家编写的高质量示范。
- 强模型生成、专家修改后的示范。
- 模型自我批评、重新生成，再由人审核的修订数据。
- 数学、代码、检索、工具调用等可验证轨迹。
- 安全拒绝与“拒绝后如何继续帮助”的边界样本。

每条数据最好保留结构化元数据：

```text
prompt
response
task_type
difficulty
language
risk_level
tool_trace
source
quality_tags
annotator_id
```

SFT 数据追求的是质量和覆盖率，而不是简单堆数量。低质量示范会直接教会模型错误的表达习惯。

### 2.2 偏好数据

对于同一个 prompt，从不同模型、不同 checkpoint、不同温度生成多个候选：

```text
prompt → response A / response B / response C ...
```

标注者根据统一 rubric 做 pairwise 或 listwise 排序，同时允许：

- A 更好
- B 更好
- 平局
- 两个都不合格
- 无法判断

标注时要特别控制以下偏差：

- 随机交换 A/B 位置，避免位置偏差。
- 不让 chosen 总是更长，避免长度成为奖励捷径。
- 隐藏模型名称和生成来源。
- 混入少量 gold questions 检查标注质量。
- 对分歧样本进行复审，而不是强行多数投票。
- 保存偏好原因，例如“事实错误”“格式不符”“过度拒绝”。

偏好样本要覆盖“明显差异”和“困难差异”。全是明显好坏的样本，奖励模型很快达到高准确率，却学不会识别细微事实错误。

InstructGPT 使用的经典流程就是“人工示范进行 SFT → 收集模型回答排序 → 训练奖励模型 → PPO 优化”，并使用留出的真实 prompt 分布进行人工评测。[InstructGPT 论文](https://arxiv.org/abs/2203.02155)

### 2.3 安全数据

安全数据需要同时包含：

- 明确违规请求。
- 表面正常但上下文逐步升级的多轮请求。
- 合法教育、新闻、研究、医疗等容易误拒绝的请求。
- 编码、隐喻、多语言、角色扮演等绕过形式。
- 正确拒绝、错误拒绝、过度拒绝的对比数据。

只训练“拒绝危险内容”会导致模型过度拒绝，因此还要提供安全替代回答和合法边界样本。

当人工数据昂贵时，可以使用基于规则或“宪法”的 AI 反馈生成候选标签，但关键高风险样本仍需人工审查。Constitutional AI 展示了利用原则、自我批评和 AI 偏好构造训练信号的方案。[Constitutional AI](https://arxiv.org/abs/2212.08073)

### 2.4 可验证任务数据

数学、代码、结构化输出和工具任务优先使用客观奖励：

- 答案匹配。
- 单元测试、隐藏测试。
- 编译和运行结果。
- JSON Schema 验证。
- SQL 执行结果。
- 工具调用是否成功。
- 引用内容是否能在来源中找到。

但验证器本身必须进行对抗测试，避免模型通过硬编码、测试泄漏或格式漏洞“刷奖励”。

### 2.5 在线迭代数据

每轮训练后，用新策略重新生成候选，重点收集：

- 奖励模型不确定的样本。
- 多个评审模型意见不一致的样本。
- 新模型与旧模型差异最大的样本。
- 线上失败频率高的任务簇。
- 高奖励但人工认为质量差的疑似 reward hacking 样本。

同时保留历史 replay 数据，避免只追逐最新分布导致遗忘。

## 3. 训练流程怎么安排

我通常会采用分阶段方案：

### 阶段一：SFT 冷启动

让模型先学会基本指令遵循、工具格式和安全边界。SFT 质量不够时直接做 RL，探索空间太大，训练成本和不稳定性都会增加。

### 阶段二：离线偏好优化

如果偏好数据已经固定，先尝试 DPO 一类离线方法。DPO 不需要显式训练 RM，也不需要在线 rollout，工程上更简单。[DPO 论文](https://arxiv.org/abs/2305.18290)

适用于：

- 单轮对话和风格对齐。
- 数据覆盖较好。
- 训练资源有限。
- 希望快速得到稳定基线。

### 阶段三：在线 RL

当需要超越静态偏好数据的覆盖范围，或者任务可以提供在线可验证奖励时，再采用：

- PPO：多轮 Agent、过程奖励、细粒度信用分配。
- GRPO：数学、代码等可生成多个候选的 RLVR。
- 混合奖励：RM reward + rule reward + safety penalty。

训练时始终保留 KL 约束、旧能力 replay 和安全数据，防止模型为了局部奖励偏离基础模型太远。

## 4. 奖励模型怎么训练

最常见的是 Bradley–Terry 形式。给定 prompt `x`、优选回答 `y_w` 和落选回答 `y_l`：

```text
P(y_w > y_l | x)
    = sigmoid(R(x, y_w) - R(x, y_l))

Loss
    = -log sigmoid(R(x, y_w) - R(x, y_l))
```

实际项目中，我更倾向于多头奖励：

```text
R_total =
    w1 * correctness
  + w2 * instruction_following
  + w3 * helpfulness
  + w4 * style
  - w5 * safety_risk
```

这样能诊断到底是哪一项变化，而不是只看到一个不可解释的总分。严重安全违规也不应只作为一个可被其他分数抵消的软负分，而应单独做 hard gate。

## 5. 奖励模型如何评测

### 基础区分能力

在严格隔离的测试集上测：

- Pairwise accuracy。
- Log loss。
- AUC。
- 平局样本的一致性。
- 按任务、语言、难度和安全类别分桶后的准确率。
- Bootstrap 置信区间。

但 pairwise accuracy 高不等于 RM 可用于强化学习。

### 校准能力

如果 RM 给出的偏好概率是 90%，它应当大约有 90% 的概率与人类偏好一致。可测：

- Brier Score。
- Expected Calibration Error。
- Reward margin 与真实一致率的关系。
- 不同任务切片上的校准曲线。

校准较差的 RM 容易在 PPO/GRPO 中被过度利用。

### 排序能力

对同一个 prompt 的多个候选回答，评测：

- Spearman/Kendall 相关系数。
- NDCG。
- Top-1 是否选中人工最佳回答。
- Best-of-N 的人工胜率。

### OOD 和挑战集

单独构造奖励模型容易判断错误的样本：

- 长但空洞 vs 短而正确。
- 表达自信但事实错误。
- 正确拒绝 vs 过度拒绝。
- 微小代码 bug。
- 推理过程漂亮但结论错误。
- 改写、翻译、多语言和不同格式。
- 对抗性提示和 reward hacking。

RewardBench 的核心思路也是把聊天、推理、安全和 OOD 困难比较分别评测，而不是只报告一个总体准确率。[RewardBench](https://arxiv.org/abs/2403.13787)

### 反捷径测试

我会构造 counterfactual tests：

- 只改变回答长度，语义不变。
- 交换 A/B 位置。
- 删除 Markdown 装饰。
- 把正确答案换成错误答案，但保留完整推理风格。
- 加入奉承、引用和自信语气。
- 给错误答案添加“因此答案显然正确”等强断言。

如果奖励主要跟长度、格式或者自信程度变化，就不能进入 RL。

### 过优化测试

这是最重要的一项：用不同优化强度训练多组策略，然后同时画出：

```text
代理 RM 分数
人工偏好胜率
独立评审分数
KL 距离
```

如果 RM 分数持续上升，但人工胜率已经下降，就出现了 Goodhart/reward hacking。研究表明，对不完美奖励模型优化过强，真实质量可能反而下降。[Reward Model 过优化研究](https://arxiv.org/abs/2210.10760)

因此最终选择 checkpoint 时，不一定选 RM 分数最高的，而是选人工质量、安全和 KL 约束下的 Pareto 点。

## 6. 离线评测怎么做

离线评测分成四层。

### 确定性评测

适合有标准答案的任务：

- 数学正确率。
- 代码 pass@k。
- 工具调用成功率。
- Schema 合法率。
- 检索召回与引用一致性。
- 安全规则触发率。

优点是稳定、便宜、可重复，缺点是覆盖不了开放式质量。

### 人工盲评

新模型与线上基线做随机顺序的 pairwise 比较，允许平局，计算：

```text
win rate
loss rate
tie rate
net win rate = win rate - loss rate
95% confidence interval
```

同时按任务切片，避免总体提升掩盖某一重要领域退化。

### 模型评审

LLM-as-a-Judge 用于扩大评测规模，但需要：

- 用人工集校准。
- 随机交换回答顺序。
- 避免评审模型知道候选来源。
- 使用多个不同评审或多次采样。
- 对高风险、细微事实和安全问题保留人工复核。

模型评审只能作为筛选和辅助，不能成为训练奖励和最终验收的唯一裁判。

### 系统与安全门禁

同时测：

- 首 token 延迟、总延迟。
- 输出 token 数和服务成本。
- 工具调用次数、超时率。
- 幻觉和引用错误率。
- 严重安全违规率。
- 过度拒绝率。
- 核心能力回归。

发布条件应类似：

```text
总体质量达到显著提升
AND 核心能力不低于回归阈值
AND 严重安全指标无退化
AND 延迟和成本在预算内
```

## 7. 在线评测怎么做

线上评测测的是“在真实分布下是否改善用户结果”，不是简单看用户是否点了赞。

### 发布步骤

```text
Shadow traffic
→ 内部 dogfood
→ 1% canary
→ 5% / 25% / 50% 灰度
→ 全量
```

每一阶段都保留快速回滚和 kill switch。

### A/B 实验设计

- 按用户或会话随机分组，并保持 sticky assignment。
- 对照组使用当前线上模型。
- 提前定义主指标、护栏指标和实验周期。
- 不因中途数据好看而随意提前停止。
- 区分新用户、重度用户、不同国家和任务类型。

### 在线指标

主指标可以是：

- 任务完成率。
- 用户继续追问或重试率。
- 回答被复制、采纳或执行的比例。
- 人工抽检胜率。
- 工具任务最终成功率。
- 显式满意度。

护栏指标包括：

- 举报率和严重安全事件。
- 过度拒绝率。
- 幻觉或错误引用抽检率。
- 延迟、错误率和单请求成本。
- 超长回答率。
- 用户流失和会话中断。

Chatbot Arena 说明了真实用户、匿名 pairwise 对比对模型偏好评测的价值；产品 A/B 与其思想类似，但还需要加入任务成功率、安全和系统成本等业务指标。[Chatbot Arena](https://arxiv.org/abs/2403.04132)

需要注意，点赞、重试、会话时长都存在选择偏差。例如会话更长可能是用户更投入，也可能是模型一直没解决问题，所以不能只看单一代理指标。

## 8. 线上数据如何回流

线上失败样本经过脱敏和授权处理后：

```text
失败日志
→ 聚类和根因分析
→ 专家标注
→ 加入训练候选池
→ 新一轮 SFT / preference / RL
```

但必须保证：

- 线上评测集不能直接回流成训练集后继续充当评测集。
- 保留长期冻结的 golden set。
- 保存旧版本策略和奖励模型，支持回溯。
- 新版本必须重新跑全量回归。
- 用户隐私数据必须满足授权、最小化使用和保留期限要求。

一句话总结：

> 我的后训练流程是“规范驱动、数据分层、奖励可审计、离线设门禁、在线做因果验证”。奖励模型的 pairwise accuracy 只是起点，最终是否发布要看独立人工偏好、真实任务成功率、安全护栏，以及代理奖励升高时有没有出现过优化。
