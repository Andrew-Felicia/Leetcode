概括一下主流大模型的共性与差异（训练范式、推理、对齐/安全等），你怎么选型？


截至 2026-10-31，主流大模型的底层共性仍然很强，但**后训练、推理时计算、工具生态、开放程度和安全边界**的差异越来越大。很多闭源模型不会公开完整训练配方，因此以下比较以官方公开信息和工程表现为准，不把厂商宣传当作严格横评。

## 一、底层共性

主流通用大模型大多遵循这条路线：

```text
大规模预训练
→ 指令微调
→ 偏好/推理强化学习
→ 安全对齐
→ 工具调用与应用层护栏
```

### 1. 架构

多数语言模型仍以 Decoder-only Transformer 为核心：

\[
P(x)=\prod_tP(x_t\mid x_{<t})
\]

共同组件包括：

- Tokenizer；
- Token Embedding；
- RoPE 等位置编码；
- Causal Self-Attention；
- MLP 或 MoE；
- RMSNorm、残差连接；
- LM Head；
- KV Cache。

差异主要在：

- Dense 还是 MoE；
- MHA、GQA、MLA 等注意力形式；
- 上下文长度；
- 是否原生支持图像、音频和视频；
- 是否针对工具调用、代码或推理做专门训练。

### 2. 预训练目标

核心仍是预测下一个 token。训练数据通常混合：

- 网页和书籍；
- 代码；
- 数学与科学数据；
- 对话；
- 多语言数据；
- 图像—文本、音频—文本等多模态数据；
- 合成数据。

模型差异很大程度来自：

- 数据质量和配比；
- 去重与过滤；
- 代码、数学和目标语言占比；
- 合成数据质量；
- 上下文长度课程；
- 训练算力与基础设施。

### 3. 后训练

预训练模型只是“续写器”，要变成助手还需要后训练：

- SFT：用高质量指令—回答数据训练；
- RLHF：根据人类偏好训练；
- RLAIF：使用 AI 反馈；
- DPO 等偏好优化；
- RLVR：通过可验证奖励增强数学、代码等能力；
- 蒸馏：把强模型能力迁移到小模型；
- 安全数据与拒绝行为训练。

例如 Anthropic 公开的 Constitutional AI 包含监督阶段以及使用 AI 偏好的强化学习阶段；Qwen 公开过“长思维链冷启动—推理 RL—思考/非思考融合—通用 RL”的训练流程；DeepSeek-V3 公开了 MoE、MLA，以及预训练后 SFT 和 RL 的路线。[Anthropic Constitutional AI](https://www.anthropic.com/research/constitutional-ai-harmlessness-from-ai-feedback)、[Qwen3 训练说明](https://qwenlm.github.io/blog/qwen3/)、[DeepSeek-V3 官方仓库](https://github.com/deepseek-ai/DeepSeek-V3)

## 二、模型之间最重要的差异

| 维度 | 主要选择 | 实际影响 |
|---|---|---|
| 参数结构 | Dense / MoE | 质量、显存、吞吐、部署复杂度 |
| 推理模式 | 直接回答 / Thinking | 推理质量与延迟、成本之间的权衡 |
| 开放程度 | 闭源 API / 开放权重 | 数据控制、定制能力、运维责任 |
| 模态 | 文本 / 视觉 / 音频 / 视频 | 是否需要额外模型和模态转换 |
| 工具能力 | 普通生成 / Function Calling / Agent | 能否可靠执行真实操作 |
| 上下文 | 短上下文 / 长上下文 | 长文档能力、成本和注意力退化 |
| 专长 | 通用 / 代码 / 数学 / 搜索 / OCR | 专项任务的质量和效率 |
| 对齐风格 | 不同偏好和安全策略 | 拒答、语气、可控性和风险 |
| 部署 | 公有 API / 私有云 / 本地 | 合规、延迟、成本和可维护性 |

## 三、Dense 与 MoE

### Dense 模型

每个 token 都经过全部参数。

优点：

- 推理结构相对简单；
- 部署工具成熟；
- 行为较稳定；
- 小规模本地部署更容易。

缺点：

- 参数越多，每个 token 的计算量通常同步增长；
- 大模型推理成本高。

### MoE 模型

每个 token 只激活少数 Expert：

```text
Token
→ Router
→ 选择 Top-k Expert
→ 合并结果
```

优点：

- 总参数容量可以很大；
- 每 token 激活参数相对较少；
- 训练和推理可能更具计算效率。

缺点：

- Router 和负载均衡复杂；
- 多卡部署需要大量 All-to-All 通信；
- 总权重仍要占据显存或分布到多设备；
- “激活参数少”不等于单机部署容易。

因此，MoE 更适合集群和高吞吐服务，不一定适合资源有限的单卡本地部署。

## 四、普通模型与推理模型

普通指令模型倾向于直接生成答案：

```text
输入 → 立即解码 → 答案
```

推理模型会在输出前或工具调用之间使用额外推理计算：

```text
输入
→ 推理计算
→ 必要时调用工具
→ 再推理
→ 最终答案
```

推理模型更适合：

- 数学；
- 复杂代码；
- 多约束规划；
- 科学分析；
- 多轮工具调用；
- 需要自检的任务。

代价是：

- 首 token 延迟更高；
- 推理 token 增加；
- 成本更高；
- 简单任务可能“想得太多”；
- 长 Agent 流程更需要状态管理。

Google 官方文档明确指出，Thinking 会增加延迟和 token 消耗，并提供不同思考级别；当前 OpenAI 官方选型也建议把“模型能力”和“reasoning effort”作为两个独立旋钮。[Gemini Thinking](https://ai.google.dev/gemini-api/docs/thinking)、[OpenAI 模型选型](https://developers.openai.com/api/docs/guides/model-selection)

工程上我不会让所有请求默认走最强推理模式，而是做路由：

```text
简单提取、分类、改写
→ 快速小模型

复杂代码、数学、规划
→ 推理模型

高风险或低置信度
→ 强模型 + 工具验证 + 人工确认
```

## 五、闭源 API 与开放权重

### 闭源 API

代表性家族包括 OpenAI、Anthropic Claude、Google Gemini 等。

优点：

- 通常能快速获得前沿能力；
- 不需要管理 GPU 集群；
- 工具调用、结构化输出、多模态和安全能力较完整；
- 模型升级、扩容和基础设施由供应商处理。

缺点：

- 权重和完整训练配方不可见；
- 价格、限额和模型行为可能变化；
- 数据跨境、留存和审计需要确认；
- 深度定制能力有限；
- 存在供应商依赖。

### 开放权重

代表性家族包括 Llama、Qwen、DeepSeek，以及部分 Mistral 模型。

优点：

- 可以本地或私有云部署；
- 可以量化、蒸馏、LoRA 和全量微调；
- 延迟、吞吐和数据路径可控；
- 可以针对领域和硬件做深度优化；
- 便于离线环境使用。

缺点：

- “权重免费”不等于总成本低；
- 需要 GPU、推理框架、监控、升级和安全团队；
- 模型许可证不一定等同于传统开源许可证；
- 安全过滤、审计和滥用防御主要由部署方承担；
- 大型 MoE 的多卡通信和显存要求可能很高。

Meta 的模型卡也明确提醒：指令模型仍存在残余风险，实际部署需要按具体场景做安全测试并增加输入、输出护栏。[Meta Llama 模型卡](https://github.com/meta-llama/llama-models/blob/main/models/llama3/MODEL_CARD.md)

## 六、多模态差异

“支持图片”并不意味着所有模型的视觉能力相同。需要分别测试：

- OCR；
- 图表理解；
- UI 截图；
- 医学或遥感影像；
- 多图比较；
- 精确空间定位；
- 视频时间关系；
- 实时语音交互。

常见结构包括：

```text
图像/音频 Encoder
→ 投影为统一 Token
→ 语言模型处理
```

或者将视觉、音频和文本更统一地联合训练。

选型时还要区分：

- 能否只理解图片，还是也能生成图片；
- 是否支持实时流式音频；
- 是否能调用计算机界面；
- 多张高分辨率图片如何计费；
- 图片是否被压缩，细节是否丢失；
- 工具调用与多模态推理能否交错执行。

多模态任务最好直接用真实输入做评测，不能用纯文本榜单替代。

## 七、推理和服务侧的差异

模型上线后的实际体验不只由参数能力决定。

### 1. Prefill 与 Decode

- Prefill：处理完整输入，上下文越长计算越多；
- Decode：逐 token 生成，通常更受 KV Cache 和内存带宽影响。

因此要分别测：

- Time to First Token；
- 输出 token/s；
- 并发吞吐；
- 长上下文下的延迟；
- p50、p95、p99；
- KV Cache 显存占用。

### 2. 推理优化

开放权重模型可以使用：

- FP8、INT8、INT4 量化；
- Continuous Batching；
- Paged Attention；
- Prefix Cache；
- Speculative Decoding；
- Tensor/Pipeline/Expert Parallel；
- vLLM、SGLang、TensorRT-LLM、llama.cpp 等框架。

量化通常能减少显存和带宽压力，但可能损害：

- 数学精度；
- 代码生成；
- 长上下文；
- 小语种；
- 工具参数输出。

不能只看通用困惑度，应在真实任务上评估量化前后的差异。

### 3. Tool Calling

主流 API 普遍支持工具调用，但可靠性差异会体现在：

- 是否选对工具；
- 参数是否符合 Schema；
- 是否重复调用；
- 工具失败后能否恢复；
- 并行调用是否可靠；
- 多轮状态是否正确保留；
- 是否会绕过权限边界。

工具调用并不是模型真正执行函数，而是模型生成结构化调用请求，由应用执行，再把结果返回模型。例如 Mistral 官方文档描述的也是“定义工具—模型生成参数—应用执行—返回结果”的循环。[Mistral Function Calling](https://docs.mistral.ai/studio/conversations/function-calling)

## 八、对齐与安全的差异

安全不是一个开关，而是多层系统：

```text
预训练数据过滤
→ SFT / 偏好训练
→ 安全强化学习
→ 系统指令
→ 输入分类器
→ 模型生成
→ 输出分类器
→ 工具权限
→ 审计与监控
```

### 模型级对齐

包括：

- RLHF；
- RLAIF；
- Constitutional AI；
- 规则奖励；
- 安全 SFT；
- 红队数据；
- 对抗训练；
- 安全推理训练。

不同厂商的差异会表现为：

- 拒绝范围不同；
- 是否容易过度拒绝；
- 对敏感上下文的理解程度；
- 对越狱和提示注入的鲁棒性；
- 高风险任务的边界不同。

### 应用级安全

即使使用最安全的模型，也需要：

- 输入、输出过滤；
- 结构化输出与参数验证；
- 最小权限；
- 沙箱执行；
- 高风险工具人工审批；
- 提示注入防护；
- 敏感数据脱敏；
- 日志和异常检测；
- 离线安全评测；
- 线上红队和回归测试。

Google 官方安全指南强调内置过滤之外仍需后处理、人工评估和防滥用设计；OpenAI 的 Agent 安全指南同样建议组合使用结构化数据、护栏、工具审批和轨迹评测，而不是只依赖模型本身。[Gemini 安全指南](https://ai.google.dev/gemini-api/docs/safety-guidance)、[OpenAI Agent 安全指南](https://developers.openai.com/api/docs/guides/agent-builder-safety)

特别是 Agent：**模型输出一段错误文字**与**模型错误地发起付款、删除数据或发送邮件**不是同一级别的风险。

# 九、主要模型家族怎么理解

| 家族 | 更值得关注的方面 | 选型时重点确认 |
|---|---|---|
| OpenAI GPT | 通用推理、工具与 Agent、多模态、结构化输出 | 能力档位、reasoning effort、成本和延迟 |
| Anthropic Claude | 长任务、工具协作、文档与代码、Constitutional AI 路线 | 思考模式、工具行为、拒答边界 |
| Google Gemini | 多模态、长上下文、Google 生态、Thinking | 模态质量、安全配置、云端集成 |
| Meta Llama | 开放权重、生态广、便于自部署和定制 | 许可证、硬件、量化、安全栈 |
| Qwen | 开放权重、中文和多语言、Dense/MoE、Thinking 系列 | 中文业务、模型尺寸、推理模式、部署框架 |
| DeepSeek | MoE、MLA、推理模型和成本效率路线 | 多卡部署、推理框架、服务稳定性 |
| Mistral | API 与部分开放权重模型、工具和欧洲企业场景 | 模型许可、区域、部署模式、专项能力 |

这张表只适合决定“先测谁”，不能直接决定最终采购。版本迭代速度很快，同一厂商的旗舰、均衡、小型模型差异，往往大于不同厂商同档模型之间的差异。

# 十、我的实际选型方法

## 第一步：先确定硬约束

先排除不满足要求的模型：

- 是否必须本地部署；
- 数据是否允许离开指定区域；
- 是否要求中文、视觉、语音或视频；
- 输入最长多长；
- 是否需要 Function Calling；
- 是否要求固定 JSON Schema；
- 单请求延迟上限；
- 并发和吞吐要求；
- 每次成功任务的预算；
- 许可证是否允许商业使用和微调；
- 高风险操作是否支持审批和审计。

硬约束不满足，榜单再高也没有意义。

## 第二步：建立真实任务评测集

从生产数据中抽取代表性任务，覆盖：

- 常规样本；
- 困难样本；
- 长上下文；
- 模糊指令；
- 错别字和噪声；
- 多语言；
- 提示注入；
- 工具失败；
- 敏感和边界请求。

不能只测十几个“看起来不错”的 Demo。

## 第三步：定义验收指标

我至少会测：

| 类型 | 指标 |
|---|---|
| 任务质量 | 准确率、通过率、人工偏好 |
| 事实性 | 有依据答案比例、引用准确率 |
| 结构化输出 | Schema 合法率、字段正确率 |
| Agent | 工具选择率、参数正确率、任务完成率 |
| 安全 | 漏放率、误拒率、越狱成功率 |
| 性能 | TTFT、总延迟、p95、吞吐 |
| 稳定性 | 重复运行一致性、版本回归 |
| 成本 | 每次请求成本、每个成功任务成本 |

最重要的是“每个成功任务成本”：

\[
\text{Cost per success}
=
\frac{\text{总模型和工具成本}}
{\text{成功完成的任务数}}
\]

便宜模型如果需要反复重试、人工修复，最终可能更贵。

## 第四步：选择最轻的达标模型

当前 OpenAI 官方选型指南也建议：使用相同输入和验收标准比较模型与推理强度，然后保留能够达到质量门槛的最轻配置。[OpenAI 模型选型指南](https://developers.openai.com/api/docs/guides/model-selection)

实践中我通常设计三档：

```text
快速层
小模型、低成本
→ 分类、抽取、简单改写

通用层
均衡模型
→ RAG、客服、普通代码和文档

推理层
强模型、高 reasoning effort
→ 复杂分析、难代码、多步 Agent
```

根据请求复杂度、置信度和失败情况动态升级，而不是让全部流量走旗舰模型。

# 十一、按场景给出选择建议

### 通用企业助手、Agent

优先测试工具调用和结构化输出成熟的闭源 API，采用均衡模型作为默认，强推理模型处理复杂请求。必须配合权限、审批和轨迹评测。

### 大规模分类、抽取、审核

优先小型快速模型；固定 Schema；如果任务稳定且数据充足，可以蒸馏或微调。没有必要为简单任务支付旗舰推理成本。

### 数学、代码、复杂规划

优先推理模型，提高 reasoning effort，并提供：

- 编译器；
- 测试；
- 计算器；
- 搜索；
- 沙箱；
- 结果验证器。

模型“想得更久”仍不能代替外部验证。

### 中文和本地化业务

同时测试闭源 API与 Qwen、DeepSeek 等开放权重模型。重点比较：

- 中文业务术语；
- 格式遵循；
- 本地知识 RAG；
- 长文本；
- 敏感边界；
- 本地部署成本。

不要因为模型来自中文语料较强的家族，就跳过真实业务评测。

### 数据敏感或离线环境

优先开放权重、自部署模型，并计算完整 TCO：

```text
GPU
+ 推理工程
+ 监控
+ 模型升级
+ 安全
+ 值班运维
```

低并发时，API 往往更省；持续高吞吐、数据限制严格或需要深度定制时，自部署更有价值。

### RAG 知识问答

模型不是唯一关键因素。还要优化：

- 文档解析；
- Chunking；
- Embedding；
- 检索和重排；
- 引用；
- 无答案拒答；
- 权限过滤；
- 检索结果中的提示注入。

很多情况下，均衡模型配合优质检索，比旗舰模型直接“凭记忆回答”更可靠。

### 高风险决策

医疗、金融、法律、生产控制等场景不应只选“最强模型”，还要：

- 强制引用和证据；
- 使用确定性规则校验；
- 设置人工复核；
- 限制工具权限；
- 记录审计日志；
- 持续监控误拒和漏放。

最终我的选型原则是：

> **先用硬约束筛掉不能部署的模型，再用真实任务和统一评测选择“达到质量、安全和延迟门槛的最轻模型”；通过模型路由把快速模型、通用模型和推理模型组合起来。**

不要问“哪家大模型整体最好”，而要问：

> 在我的数据、工具、风险等级和成本约束下，哪个模型以最低的每任务总成本，稳定完成了最多真实任务？
