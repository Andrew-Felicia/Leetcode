请详细解释 Data Parallel（DP）和 Distributed Data Parallel（DDP）的差异。



先澄清术语：

- **数据并行 Data Parallelism** 是一种通用训练思想：复制模型、切分数据、汇总梯度。
- PyTorch 的 **`nn.DataParallel`** 是这种思想的一种单进程实现，通常简称 DP。
- PyTorch 的 **`DistributedDataParallel`** 是多进程、可跨机器的实现，简称 DDP。

所以 DDP 本身也是数据并行。大家所说的“DP 和 DDP 的区别”，通常指 PyTorch 这两个类的区别。

PyTorch 当前官方建议：即使只在单机多卡上训练，也优先使用 DDP，而不是 `nn.DataParallel`。[PyTorch DataParallel 文档](https://docs.pytorch.org/docs/main/generated/torch.nn.DataParallel.html)、[PyTorch CUDA 语义](https://docs.pytorch.org/docs/stable/notes/cuda.html)

## 1. 二者的共同思想

假设有4张 GPU，一个 global batch 有128个样本。

数据并行会把数据切成：

```text
GPU 0：32个样本
GPU 1：32个样本
GPU 2：32个样本
GPU 3：32个样本
```

每张 GPU 都持有完整模型：

```text
GPU 0：完整模型副本
GPU 1：完整模型副本
GPU 2：完整模型副本
GPU 3：完整模型副本
```

每个副本分别执行：

```text
局部前向传播
→ 局部 Loss
→ 局部反向传播
→ 局部梯度
```

然后聚合梯度，使各 GPU 使用相同梯度更新参数。

因此前提是：

> 完整模型、单卡 batch 和训练激活必须能放进一张 GPU。

如果模型本身放不进单卡，应考虑 FSDP、Tensor Parallel 或 Pipeline Parallel，而不是普通 DP/DDP。

# 2. DataParallel 的执行方式

`nn.DataParallel` 使用：

```text
一个 Python 进程
+ 多个工作线程
+ 多张 GPU
```

默认以 `device_ids[0]`，通常是 GPU 0，作为主设备。

一个 iteration 大致执行：

```text
主进程取得完整 batch
        ↓
scatter：把 batch 分发到多张 GPU
        ↓
replicate：在每张 GPU 创建模型副本
        ↓
每张 GPU 并行前向
        ↓
gather：把输出收集到 GPU 0
        ↓
计算 Loss
        ↓
每张 GPU 反向传播
        ↓
梯度汇总到 GPU 0 上的原始模型
        ↓
GPU 0 上的 optimizer 更新参数
```

## DataParallel 示例

```python
import torch
from torch import nn

device = torch.device("cuda:0")

model = MyModel().to(device)

model = nn.DataParallel(
    model,
    device_ids=[0, 1, 2, 3],
)

optimizer = torch.optim.AdamW(
    model.parameters(),
    lr=1e-4,
)

for x, y in dataloader:
    x = x.to(device)
    y = y.to(device)

    optimizer.zero_grad()

    prediction = model(x)
    loss = loss_fn(prediction, y)

    loss.backward()
    optimizer.step()
```

使用简单，但存在明显性能和扩展问题。

# 3. DistributedDataParallel 的执行方式

DDP 通常使用：

```text
一张 GPU 对应一个独立 Python 进程
```

4张 GPU 对应：

```text
进程 rank 0 → GPU 0
进程 rank 1 → GPU 1
进程 rank 2 → GPU 2
进程 rank 3 → GPU 3
```

每个进程拥有：

- 完整模型副本；
- 自己的 optimizer；
- 自己的 DataLoader；
- 自己的数据子集；
- 独立的 Python 解释器；
- 独立的 CUDA Context。

一个 iteration 大致执行：

```text
rank 0：读取数据子集 0 → 前向 → 反向
rank 1：读取数据子集 1 → 前向 → 反向
rank 2：读取数据子集 2 → 前向 → 反向
rank 3：读取数据子集 3 → 前向 → 反向

反向过程中：
各 rank 通过 All-Reduce 同步梯度

同步完成后：
每个 rank 都得到相同的平均梯度

然后：
每个 rank 独立执行相同 optimizer.step()
```

DDP 不负责自动切分输入数据，需要用户使用 `DistributedSampler` 等方式保证不同 rank 读取不同样本。[PyTorch DDP 文档](https://docs.pytorch.org/docs/main/generated/torch.nn.parallel.DistributedDataParallel.html)

---

# 4. DDP 为什么不需要每步广播参数

初始化时，DDP 会让各个进程的模型参数保持一致。

训练过程中：

```text
初始参数相同
+
各 rank 得到相同的聚合梯度
+
各 rank 使用相同 optimizer 状态和更新规则
=
更新后参数仍然相同
```

所以每一步不需要把 rank 0 的参数重新广播到其他 GPU。

PyTorch DDP 主要同步的是梯度，而不是每一步重新同步全部参数。

默认情况下：

- 构造 DDP 时同步初始模型状态；
- 反向传播时 All-Reduce 梯度；
- 每个 rank 本地执行 optimizer step；
- 模型 buffer，例如部分 BatchNorm buffer，默认可能从 rank 0 广播。

---

# 5. 梯度 All-Reduce 是怎么做的

假设4个 rank 的某个参数梯度分别是：

```text
g0、g1、g2、g3
```

DDP 执行类似：

```text
g_global = (g0 + g1 + g2 + g3) / 4
```

最终每个 rank 都获得：

```text
rank 0：g_global
rank 1：g_global
rank 2：g_global
rank 3：g_global
```

然后每个 rank 都执行：

```text
W = W - learning_rate × g_global
```

参数因此继续保持一致。

GPU 场景下通常使用 NCCL Backend。PyTorch 官方文档也将 NCCL列为GPU训练的推荐后端。[PyTorch DDP 文档](https://docs.pytorch.org/docs/main/generated/torch.nn.parallel.DistributedDataParallel.html)

---

# 6. DDP 如何重叠反向计算和通信

如果等所有层都完成反向传播后再统一通信，GPU 和网络会串行等待：

```text
完整 backward
→ 完整梯度通信
→ optimizer step
```

DDP 会把参数梯度组织成多个 Bucket。

反向传播通常从输出层向输入层进行。当一个 Bucket 中的梯度都准备好后，DDP 可以立刻开始 All-Reduce，同时继续计算前面层的梯度：

```text
计算后层梯度
→ Bucket 1 准备好
→ 开始通信 Bucket 1
   同时计算前层梯度
→ Bucket 2 准备好
→ 开始通信 Bucket 2
```

即：

```text
梯度计算和梯度通信重叠
```

这是 DDP 通常比 DataParallel 更快的重要原因之一。DDP 内部通过 Reducer 和梯度 Bucket 完成这套机制。[PyTorch DDP 内部设计](https://docs.pytorch.org/docs/stable/notes/ddp.html)

# 7. 核心差异对比

| 维度 | DataParallel | DistributedDataParallel |
|---|---|---|
| 进程模型 | 单进程、多线程 | 通常每张 GPU 一个进程 |
| Python 解释器 | 所有 GPU 共享 | 每个 GPU 独立 |
| GIL 影响 | 明显 | 基本避免跨 GPU 线程争用 |
| 使用范围 | 单机多卡 | 单机多卡、跨节点多卡 |
| 数据切分 | DP 自动 scatter | 用户使用 DistributedSampler |
| 模型副本 | 每次 forward 复制或管理副本 | 每个进程持久拥有一个副本 |
| 输出处理 | 默认 gather 到主 GPU | 各 rank 保留自己的输出 |
| 梯度同步 | 汇总到主模型 | All-Reduce 到所有 rank |
| Optimizer | 主进程一个 optimizer | 每个 rank 一个 optimizer |
| 通信重叠 | 能力较弱 | Bucket All-Reduce 可与反向重叠 |
| GPU 0 负载 | 通常明显更高 | 各 GPU 更均衡 |
| 多机扩展 | 不支持 | 支持 |
| 易用性 | 非常简单 | 初始化和调试更复杂 |
| 官方推荐 | 不推荐作为多卡默认 | 多卡训练默认选择 |

# 8. 为什么 DataParallel 通常更慢

## 单进程和 GIL

DataParallel 使用线程驱动多张 GPU。Python 逻辑较多、模型由许多小模块组成时，线程会受到 Python GIL 和调度开销影响。

DDP 每个进程有独立 Python 解释器，可以减少这类竞争。

## GPU 0 成为瓶颈

DataParallel 通常在主 GPU 上执行额外工作：

- 持有原始模型；
- 接收完整输入；
- Scatter 输入；
- Gather 输出；
- 汇总梯度；
- 执行 optimizer step；
- 可能计算完整 Loss。

因此 GPU 0 的：

- 显存；
- 通信；
- 计算；
- 内存带宽；

压力通常高于其他 GPU。

## 模型复制和 Gather 开销

DataParallel 在每次 forward 中需要管理或复制模型副本，并把输出重新收集到主设备。

DDP 的模型副本在每个进程中持久存在，也不需要默认把输出集中到一张 GPU。

## 通信与计算重叠较弱

DDP 能在反向传播过程中按 Bucket 启动 All-Reduce；DataParallel 的中心式汇总更容易形成串行瓶颈。

# 9. 显存差异

## DataParallel

所有 GPU 都要保存完整模型副本，但 GPU 0 通常额外保存或承担：

- 原始模型；
- Gather 后的输出；
- 目标标签；
- Loss；
- 聚合梯度；
- optimizer 状态；
- 其他主设备张量。

因此显存可能类似：

```text
GPU 0：模型 + 激活 + 输出汇总 + optimizer + 额外开销
GPU 1：模型副本 + 局部激活
GPU 2：模型副本 + 局部激活
GPU 3：模型副本 + 局部激活
```

容易出现：

```text
GPU 0 OOM
其他 GPU 还有很多空闲显存
```

## DDP

每个 rank 通常都有：

```text
完整模型
完整 optimizer 状态
局部 batch 激活
局部梯度
梯度通信 Bucket
```

显存分布更均衡，但每张 GPU 仍然需要容纳完整模型和 optimizer。

DDP 不是参数分片方案。

如果模型不能放入单卡：

- FSDP：分片参数、梯度和 optimizer state；
- Tensor Parallel：切分层内矩阵；
- Pipeline Parallel：按层切分模型。

PyTorch 当前分布式概览也建议：模型能放入单 GPU 时使用 DDP；模型放不下时考虑 FSDP。[PyTorch Distributed Overview](https://docs.pytorch.org/tutorials/beginner/dist_overview.html)

# 10. Batch Size 的含义

DDP 中，每个 rank 的 DataLoader `batch_size` 通常指单进程 batch。

假设：

```text
per_rank_batch = 32
world_size = 4
gradient_accumulation_steps = 2
```

有效 global batch：

```text
global_batch
=
per_rank_batch
× world_size
× gradient_accumulation_steps

=
32 × 4 × 2
=
256
```

这是迁移到 DDP 时最容易忽略的问题之一。

## 两种迁移方式

### 保持每卡 batch 不变

单卡原来：

```text
batch = 32
```

4卡 DDP 每卡仍为32：

```text
global batch = 128
```

这提高吞吐，但改变了优化问题，可能需要调整：

- 学习率；
- Warmup；
- 正则化；
- 训练轮数或总 step。

### 保持 global batch 不变

单卡原来：

```text
global batch = 32
```

4卡时每卡：

```text
per_rank_batch = 8
```

这样数学上更接近原训练，但每卡 batch 太小时 GPU 利用率可能下降，BatchNorm 也可能不稳定。

# 11. DDP 梯度和单卡是否完全等价

假设：

- 每个 rank 的 batch size 相同；
- loss 使用 batch mean；
- 所有 rank 执行相同数量的 iteration；
- 随机层和 BatchNorm 差异可忽略；
- DDP 对梯度求平均。

则 DDP 梯度等价于对 global batch 求平均后的梯度。

例如两个 rank：

```text
rank 0：
g0 = (g1 + g2) / 2

rank 1：
g1 = (g3 + g4) / 2
```

DDP 平均：

```text
g =
(g0 + g1) / 2

=
(g1 + g2 + g3 + g4) / 4
```

与单卡使用4个样本的 mean loss 等价。

## 不等长本地 Batch

如果：

```text
rank 0 有32个样本
rank 1 有8个样本
```

DDP 默认平均两个 rank 的梯度，而不是自动按样本数加权。

这时结果不一定等价于40个样本的全局平均。通常应通过 sampler、`drop_last` 或显式加权保证一致性。

## Loss 使用 Sum

如果每个 rank 的 loss 是 sum 而不是 mean，梯度尺度也需要单独分析。最稳妥的是明确：

- Loss 在哪些维度求和；
- 哪些维度求平均；
- DDP 是否再除以 world size；
- 梯度累积是否又做缩放。

# 12. DistributedSampler

DDP 不自动切分数据。

如果每个进程都使用普通 DataLoader：

```text
rank 0 读取完整数据
rank 1 也读取完整数据
rank 2 也读取完整数据
rank 3 也读取完整数据
```

就会重复训练相同样本，global batch 并没有真正扩大。

应该使用：

```python
from torch.utils.data.distributed import DistributedSampler

sampler = DistributedSampler(
    dataset,
    shuffle=True,
)

dataloader = DataLoader(
    dataset,
    batch_size=per_rank_batch,
    sampler=sampler,
    shuffle=False,
)
```

`DistributedSampler` 负责让不同 rank 获取不同的数据索引。

每个 epoch 开始时还应调用：

```python
sampler.set_epoch(epoch)
```

否则多个 epoch 可能使用相同的 shuffle 顺序。PyTorch 官方多 GPU 教程也特别强调了这一点。[PyTorch DDP 多 GPU 教程](https://docs.pytorch.org/tutorials/beginner/ddp_series_multigpu.html)

# 13. DDP 基础代码

启动：

```bash
torchrun --standalone --nproc-per-node=4 train.py
```

训练脚本：

```python
import os

import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel
from torch.utils.data import DataLoader
from torch.utils.data.distributed import DistributedSampler


def main():
    # torchrun 会提供 RANK、LOCAL_RANK、WORLD_SIZE
    dist.init_process_group(backend="nccl")

    rank = dist.get_rank()
    world_size = dist.get_world_size()
    local_rank = int(os.environ["LOCAL_RANK"])

    torch.cuda.set_device(local_rank)
    device = torch.device(f"cuda:{local_rank}")

    dataset = MyDataset()

    sampler = DistributedSampler(
        dataset,
        num_replicas=world_size,
        rank=rank,
        shuffle=True,
    )

    dataloader = DataLoader(
        dataset,
        batch_size=32,       # 每个 rank 的 batch
        sampler=sampler,
        shuffle=False,
        num_workers=4,
        pin_memory=True,
    )

    model = MyModel().to(device)

    model = DistributedDataParallel(
        model,
        device_ids=[local_rank],
        output_device=local_rank,
    )

    optimizer = torch.optim.AdamW(
        model.parameters(),
        lr=1e-4,
    )

    for epoch in range(num_epochs):
        sampler.set_epoch(epoch)
        model.train()

        for x, y in dataloader:
            x = x.to(device, non_blocking=True)
            y = y.to(device, non_blocking=True)

            optimizer.zero_grad(set_to_none=True)

            prediction = model(x)
            loss = loss_fn(prediction, y)

            loss.backward()
            optimizer.step()

        if rank == 0:
            print(f"epoch={epoch}")

    if rank == 0:
        # 保存原始模型，不保存 DDP wrapper
        torch.save(
            model.module.state_dict(),
            "model.pt",
        )

    dist.destroy_process_group()


if __name__ == "__main__":
    main()
```

# 14. Loss 日志需要显式聚合

DDP 会同步参数梯度，但不会自动把你打印的 Loss 聚合。

每个 rank 得到的是自己的 local loss：

```text
rank 0：loss = 0.8
rank 1：loss = 1.1
rank 2：loss = 0.9
rank 3：loss = 1.2
```

如果只打印 rank 0：

```python
if rank == 0:
    print(loss.item())
```

看到的只是 rank 0 的 loss，不是全局平均。

可以显式聚合：

```python
loss_for_log = loss.detach().clone()

dist.all_reduce(
    loss_for_log,
    op=dist.ReduceOp.SUM,
)

loss_for_log /= dist.get_world_size()

if rank == 0:
    print(loss_for_log.item())
```

如果不同 rank 的 batch size 不同，还要根据有效样本数或有效 token 数做加权，而不能简单平均 rank loss。

# 15. 梯度累积与 `no_sync()`

如果使用梯度累积：

```text
累计4个 micro-batch
→ 再执行一次 optimizer step
```

默认 DDP 会在每次 `backward()` 后同步梯度，这会产生不必要通信。

可以对前几个 micro-batch 使用：

```python
with model.no_sync():
    prediction = model(x)
    loss = loss_fn(prediction, y)
    loss = loss / accumulation_steps
    loss.backward()
```

最后一个 micro-batch 正常执行：

```python
prediction = model(x)
loss = loss_fn(prediction, y)
loss = loss / accumulation_steps
loss.backward()

optimizer.step()
optimizer.zero_grad(set_to_none=True)
```

注意：官方文档要求 forward 也应放在 `no_sync()` 上下文中，否则仍可能触发同步。[PyTorch DDP `no_sync`](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)

# 16. BatchNorm 的差异

普通 DDP 中，每个 rank 的 BatchNorm 使用自己的 local batch 统计量：

```text
rank 0：根据本地32个样本计算均值和方差
rank 1：根据本地32个样本计算均值和方差
```

并不会自动用 global batch 的全部样本统计。

当每卡 batch 很小时，BatchNorm 可能不稳定。

可选方案：

- 使用 `SyncBatchNorm`；
- 使用 GroupNorm；
- 使用 LayerNorm；
- 冻结预训练模型的 BatchNorm；
- 增大每卡 batch。

SyncBatchNorm 会增加额外通信，因此是否值得要看任务和每卡 batch 大小。

# 17. 动态分支和未使用参数

DDP 假设各 rank 以一致顺序执行对应的梯度同步。

如果模型有条件分支：

```python
if condition:
    output = branch_a(x)
else:
    output = branch_b(x)
```

可能出现某些参数在本轮没有参与 Loss。

这时可能需要：

```python
DistributedDataParallel(
    model,
    device_ids=[local_rank],
    find_unused_parameters=True,
)
```

但该选项会增加计算图遍历开销。

更重要的问题是：如果不同 rank 进入不同分支，可能导致：

- Collective 调用不匹配；
- 某些梯度不同步；
- 训练挂起；
- 参数行为不一致。

如果计算图固定，可以考虑 `static_graph=True`，但应先确认训练图确实稳定。

# 18. 为什么 DDP 容易“卡死”

DDP 的许多操作是 Collective：

```text
所有 rank 必须按相同顺序参与
```

例如 rank 0 执行：

```text
All-Reduce A
All-Reduce B
```

rank 1 却只执行：

```text
All-Reduce A
```

那么 rank 0 会一直等待 rank 1 参与 B。

常见原因：

- 某个 rank 数据提前耗尽；
- 某个 rank 出现异常但其他 rank 继续运行；
- 不同 rank 走了不同分支；
- 只在 rank 0 调用了包含 Collective 的代码；
- 某个 rank 跳过 backward；
- DataLoader worker 死锁；
- 参数在不同进程中注册顺序不同。

调试时可以设置：

```bash
TORCH_DISTRIBUTED_DEBUG=DETAIL
NCCL_DEBUG=INFO
```

并让所有日志包含：

```text
rank
global step
当前 batch
进入/退出 forward
进入/退出 backward
```

# 19. Checkpoint 怎么保存和恢复

通常只让 rank 0 写文件：

```python
if rank == 0:
    torch.save(
        {
            "model": model.module.state_dict(),
            "optimizer": optimizer.state_dict(),
            "epoch": epoch,
            "step": step,
        },
        checkpoint_path,
    )
```

恢复时每个 rank 都需要获得一致状态：

```python
checkpoint = torch.load(
    checkpoint_path,
    map_location=device,
)

model.module.load_state_dict(checkpoint["model"])
optimizer.load_state_dict(checkpoint["optimizer"])
```

还应根据需求恢复：

- scheduler；
- GradScaler；
- global step；
- sampler 或数据进度；
- 随机数状态。

注意 DDP 包装后的参数名常带有 `module.` 前缀。保存 `model.module.state_dict()` 通常更便于非 DDP 环境加载。

# 20. DDP 的性能瓶颈

DDP 的理想加速不是 GPU 数量的严格线性倍数。

扩展效率近似为：

```text
scaling efficiency
=
单卡耗时
/
(多卡耗时 × GPU 数量)
```

性能损失来自：

- 梯度 All-Reduce；
- 跨节点网络；
- 小 batch 导致 GPU 利用率不足；
- 数据加载；
- 不均衡的输入长度；
- Rank 之间等待；
- 过多小梯度 Bucket；
- Python 和 CPU 预处理；
- 同步 BatchNorm；
- Checkpoint 和日志。

## DDP 更适合的情况

- 模型计算量大；
- 单卡 batch 足够；
- 每步计算时间明显大于通信时间；
- GPU 之间有高速互联；
- 多节点网络良好；
- 数据长度相对均衡。

## 扩展效果差的情况

- 模型很小；
- 每卡 batch 很小；
- 参数多但计算量低；
- 大量小算子；
- 跨节点带宽低；
- 每个 rank 的序列长度差异大；
- 频繁执行额外 Collective。

# 21. 实际怎么选

## 单 GPU

不需要 DP 或 DDP：

```python
model.to(device)
```

## 单机多 GPU，快速验证旧代码

`nn.DataParallel` 可以用很少代码运行，但只适合：

- 临时实验；
- 模型较简单；
- 性能要求不高；
- 不打算扩展到多节点。

## 正式单机多 GPU 训练

优先 DDP：

- 性能更好；
- GPU 负载更均衡；
- 与多节点训练方式一致；
- 通信可与反向计算重叠；
- 官方推荐。

## 多节点训练

使用 DDP、FSDP 或其他分布式并行方案。DataParallel 不支持跨节点。

## 模型放不进单卡

DDP 也解决不了，因为每个 rank 仍持有完整模型。考虑：

```text
FSDP
Tensor Parallel
Pipeline Parallel
ZeRO
```

## 一句话总结

```text
DataParallel：
一个进程控制多张 GPU，
自动切数据、集中输出和梯度，
简单，但主 GPU 和 Python 调度容易成为瓶颈。

DistributedDataParallel：
每张 GPU 一个进程，
各自读取不同数据，
反向时用 All-Reduce 同步梯度，
性能、负载均衡和多机扩展都更好。
```

实际项目中，如果模型能装入单张 GPU、但希望用多张 GPU 扩展训练，我会直接以 DDP 作为默认方案。
