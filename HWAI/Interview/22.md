强化学习后训练里，为何选择 PPO 而不是 GRPO？两者目标函数、稳定性与实现复杂度有哪些关键差别？


核心结论：PPO 和 GRPO 的主要区别不在“有没有 clipping”，而在于“优势函数怎么估计”。

- 如果是多轮交互、工具调用、过程奖励，或者每个 prompt 只能生成少量轨迹，我更倾向 PPO。
- 如果是数学、代码等结果可验证任务，能够为同一 prompt 生成多个候选，而且显存紧张，我更倾向 GRPO。
- GRPO 不是全面升级版 PPO：它省掉了 Critic，却把一部分成本转移到了多样本生成和组内统计上。

## 1. PPO 的目标函数

PPO 使用 rollout 时的旧策略 `pi_old` 采样，然后优化当前策略 `pi_theta`：

```text
rho_t = pi_theta(a_t | s_t) / pi_old(a_t | s_t)

J_clip =
E[min(
    rho_t * A_t,
    clip(rho_t, 1-eps, 1+eps) * A_t
)]
```

当优势 `A_t > 0` 时，提高该动作概率；`A_t < 0` 时降低概率。`clip` 防止新旧策略一次偏离太远，使同一批 rollout 可以进行多个 minibatch、多个 epoch 的更新。[PPO 原论文](https://arxiv.org/abs/1707.06347)

在典型的 LLM PPO 中，优势由 Critic/Value Model 和 GAE 计算：

```text
delta_t = r_t + gamma * V(s_{t+1}) - V(s_t)

A_t^GAE =
delta_t
+ gamma*lambda*delta_{t+1}
+ (gamma*lambda)^2*delta_{t+2}
+ ...
```

完整损失通常还包括：

```text
Loss =
    - Policy_Clip_Loss
    + c_v * Value_Loss
    - c_e * Entropy
    + beta * KL(pi_theta || pi_ref)
```

其中：

- `pi_old`：本轮生成数据时的策略，用于重要性比率和 clipping。
- `pi_ref`：通常是冻结的 SFT 模型，用于防止策略长期漂移。
- 两者不是同一个概念。

## 2. GRPO 的目标函数

GRPO 对同一个 prompt 生成 `G` 个回答：

```text
o_1, o_2, ..., o_G ~ pi_old
```

得到奖励：

```text
r_1, r_2, ..., r_G
```

不训练 Critic，而是用组内均值作为 baseline：

```text
A_i = (r_i - mean(r_1...r_G)) / (std(r_1...r_G) + eps)
```

然后仍使用 PPO 风格的 clipped objective：

```text
rho_i,t = pi_theta(token_i,t) / pi_old(token_i,t)

J_GRPO =
E[
  mean_over_groups_and_tokens(
      min(
          rho_i,t * A_i,
          clip(rho_i,t, 1-eps, 1+eps) * A_i
      )
      - beta * KL(pi_theta || pi_ref)
  )
]
```

在最常见的 outcome-reward GRPO 中，一个回答的所有 token 共用同一个 `A_i`。原始论文也提出了 process supervision 版本，可以给不同推理步骤计算不同优势。[DeepSeekMath 的 GRPO 定义](https://arxiv.org/abs/2402.03300)

所以可以把 GRPO 理解成：

```text
PPO 的 clipped policy update
+ 组内相对奖励
- Critic / Value Model / GAE
```

## 3. 为什么某些场景选择 PPO

### 多轮环境需要时间信用分配

例如模型连续执行：

```text
思考 → 调工具 → 观察结果 → 再调用工具 → 最终回答
```

最终失败可能是第二次工具调用造成的。PPO 的 Critic 和 GAE 可以为不同时间步估计不同优势，更适合这种序列决策。

Outcome-GRPO 通常把一个最终奖励广播给整个回答，容易把正确结果之前的无关 token 也一起强化。

### 每个 prompt 不能生成很多候选

GRPO 依赖组内比较。如果 `G` 很小，均值和标准差估计会很噪；如果只能生成一个回答，根本无法形成组内 baseline。

PPO 可以利用跨 prompt 训练出来的价值函数，即使每个 prompt 只有一个或少数 rollout，也能估计优势。

### 奖励容易饱和

假设是二值正确性奖励：

```text
组 A：[1, 1, 0, 0]  → 有明确相对信号
组 B：[0, 0, 0, 0]  → std = 0，基本没有学习信号
组 C：[1, 1, 1, 1]  → 同样没有组内区分
```

当模型太弱或者太强时，GRPO 很容易遇到全错组或全对组。PPO 的 Critic原则上还能利用跨样本的绝对回报差异，但前提是 Critic 确实学得准。

### Critic 有机会学到可靠状态价值

如果存在密集过程奖励、清晰的中间状态或者大量相似轨迹，Critic 能有效降低策略梯度方差。这时舍弃 Critic 未必划算。

### 已有成熟的 PPO 基础设施

PPO 的训练、诊断体系比较成熟，可以监控：

- policy KL
- value loss
- explained variance
- clip fraction
- entropy
- advantage statistics

如果团队已经有稳定的 actor-critic 系统，改成 GRPO 不一定能节省整体工程成本。

## 4. 两者稳定性的差别

| 维度 | PPO | GRPO |
|---|---|---|
| 优势 baseline | 学习得到的 `V(s)` | 同一 prompt 的组内均值 |
| 方差来源 | Critic 误差、GAE 参数 | 组大小、采样随机性、组内奖励方差 |
| 偏差风险 | Critic 预测错误带来偏差 | 相对归一化可能强化“差组里的最好答案” |
| 信用分配 | 可做到 token/时间步级 | Outcome 版本通常是回答级 |
| 奖励尺度 | 需要 reward/value normalization | 组内标准化自动消除部分尺度差异 |
| 典型故障 | Value loss 爆炸、策略与 Critic 不同步 | 全对/全错组无信号，小标准差导致不稳定 |

PPO 的主要不稳定源是 Critic：

- Value Model 与策略同时变化，目标非平稳。
- 终局奖励很难从中间 token 预测。
- GAE 的 `lambda`、value clipping、value loss 权重都需要调整。

GRPO 删除 Critic，因此没有 value collapse、critic overfitting 等问题；但会产生新的敏感项：

- group size `G`
- sampling temperature
- 组内奖励标准差
- 二值奖励的通过率
- 长度归一化
- 相同 prompt 的候选能否被正确分配到同一个分布式 worker/group

DeepSeek-R1 的一个实验中，PPO 对 GAE 的 `lambda` 非常敏感：`lambda=0.95` 明显较差，调到 `1.0` 后接近 GRPO。但这是特定模型和任务上的结果，不能直接推广成“PPO 总是不稳定”。[DeepSeek-R1 的 PPO/GRPO 对比](https://arxiv.org/abs/2501.12948)

## 5. 实现复杂度与真实成本

典型 PPO-RLHF 需要：

```text
Actor
Old policy log-probs
Reference model
Critic / Value Model
Reward Model 或规则验证器
GAE / returns
Policy loss + value loss + KL
```

复杂点主要是：

- Critic 通常与 Actor 同量级，显存和计算昂贵。
- 要维护独立 optimizer、checkpoint 和并行策略。
- Actor、Critic 必须使用一致的 token mask、padding 和序列边界。
- Value targets、GAE 和终止状态很容易实现出错。

GRPO 通常需要：

```text
Actor
Old policy log-probs
Reference model
Reward Model 或规则验证器
每个 prompt 的 G 个回答
组内 reward normalization
Clipped policy loss + KL
```

它少了 Critic、GAE 和 Value Loss，模型侧明显简单，也能节省显存；DeepSeekMath 提出 GRPO 的核心动机正是去掉与策略模型规模相近的价值模型。[DeepSeekMath](https://arxiv.org/abs/2402.03300)

但 GRPO 并不是“计算免费”：

- 每个 prompt 必须生成多个完整回答。
- 长 CoT 场景下，rollout 解码可能才是最大成本。
- `G` 越大，优势估计越稳定，但生成成本越高。
- 分布式训练必须保证同一 prompt 的样本能够正确分组。

因此更准确的说法是：

```text
GRPO：降低训练侧的模型内存和 Critic 计算
      增加 rollout 数量及组管理压力

PPO：增加 Critic 训练成本
     但不强制每个 prompt 生成大量候选
```

## 6. 我的实际选型标准

我会选择 PPO，当：

- 任务是多轮 Agent、游戏、机器人或工具调用。
- 有密集过程奖励，需要时间步级信用分配。
- 每个 prompt 的 rollout 数很有限。
- Reward 非常噪，组内排序不稳定。
- Critic 可以训练得比较可靠，显存也能承担。

我会选择 GRPO，当：

- 任务是数学、代码、定理证明等 RLVR。
- 最终结果可以由答案匹配、单元测试或执行器可靠验证。
- 可以为每个 prompt 生成多个候选。
- 大模型 Critic 的显存和计算成本不可接受。
- 主要目的是学习“同一道题哪些推理更好”。

一句面试式总结：

> PPO 用学习出来的价值函数换取更细粒度、更跨样本的优势估计，代价是 Critic 的显存、计算和训练不稳定性；GRPO 用同一 prompt 下多个回答的相对奖励替代 Critic，模型侧更简单，但依赖足够多且有差异的组内样本，生成成本更高，对结果可验证、单轮推理任务尤其合适。
