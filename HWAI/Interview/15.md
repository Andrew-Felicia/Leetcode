KV Cache 在训练和推理中的差异是什么？它的加速价值有多大，吞吐与延迟你是如何权衡的，vLLM/paged‑attention 需要注意什么。


先给结论：

> **标准训练基本不使用“跨 token 持久化”的 KV Cache；自回归推理中 KV Cache 几乎是必需的。它把每个解码步从“重算全部历史 token”变为“只计算新 token，并读取历史 K/V”，代价是大量显存占用和内存带宽。**

PagedAttention 不会消除 KV Cache，也不会减少逻辑上的注意力计算；它主要解决 KV Cache 的**动态分配、碎片、共享和并发容量**问题。

## 1. K、V 到底是什么

每层 Self-Attention 会从隐藏状态生成：

```text
Q = X × Wq
K = X × Wk
V = X × Wv
```

注意力为：

```text
Attention(Q, K, V)
= softmax(Q × K^T / sqrt(d)) × V
```

生成第 `t` 个 token 时，当前 Query 要查询所有历史 token：

```text
q_t 查询 [k_1, k_2, ..., k_t]
再加权读取 [v_1, v_2, ..., v_t]
```

历史 token 的 K、V 一旦由固定模型算出，在本次生成过程中不会变化，因此可以缓存。

---

# 2. 训练中的 K/V

标准自回归训练采用 Teacher Forcing：

```text
输入： A B C D
目标： B C D E
```

虽然有 causal mask，但所有位置可以在一次前向中并行计算：

```text
Q = [q1, q2, q3, q4]
K = [k1, k2, k3, k4]
V = [v1, v2, v3, v4]
```

然后一次性计算整个 causal attention。

训练中的 K、V：

- 是当前前向传播的中间激活；
- 反向传播可能需要它们；
- 当前 step 完成后通常释放；
- 不会跨训练 step 长期保留；
- 可能被 activation checkpointing 丢弃，反向时重新计算。

这更准确地称为“训练激活”，而不是推理意义上的 KV Cache。

## 为什么训练不用持久 KV Cache

### 所有 token 已经并行计算

训练时没有必要按 token 一个一个生成。把前缀缓存下来再逐 token 计算，反而会破坏 GPU 最擅长的大矩阵并行。

### 参数每一步都会变化

训练 step 更新参数后：

```text
Wk、Wv 已经改变
```

旧参数生成的 K、V 对新参数来说已经过期，不能安全地跨 step 复用。

### 每个训练样本通常只使用一次

普通训练 batch 之间没有大量完全相同的前缀，复用价值很低。

### 训练需要梯度图

推理缓存通常是只读张量，不保留完整反向计算图。训练如果跨 step 保留计算图，会导致巨大的显存占用和错误的梯度依赖。

## 训练中也可能看到 KV Cache 的情况

以下过程本质上包含“推理阶段”，可以使用缓存：

- RLHF/RLVR 中生成 rollout；
- 在线蒸馏时由 Teacher 生成答案；
- 长文本流式评估；
- 推理式数据生成；
- 某些递归或流式 Transformer；
- 训练前后的验证生成。

但“生成 rollout 使用 KV Cache”和“对 rollout 做反向训练”是两个不同阶段。

---

# 3. 推理中的 Prefill 与 Decode

推理通常分成两阶段。

## Prefill

把整个 Prompt 并行送入模型：

```text
Prompt：A B C D
→ 一次前向
→ 得到每一层所有位置的 K、V
→ 写入 KV Cache
→ 输出第一个新 token
```

Prefill 特点：

- 矩阵规模大；
- 并行度高；
- 通常更偏计算密集；
- 决定 Time to First Token 的主要部分。

普通 KV Cache 不会让首次 Prefill 更快，因为缓存本身正是在 Prefill 中创建的。

只有当相同前缀被其他请求复用时，Prefix Caching 才能跳过部分 Prefill。

## Decode

之后每一步只输入最新 token：

```text
新 token
→ 只计算它的 q_t、k_t、v_t
→ q_t 读取全部历史 KV Cache
→ 得到下一个 token
→ 把新的 k_t、v_t 追加到缓存
```

Decode 特点：

- 每次通常只生成一个 token；
- 矩阵较小；
- 必须读取模型权重和历史 KV；
- 常受显存带宽限制；
- 决定 Inter-Token Latency / TPOT。

---

# 4. KV Cache 加速了什么

假设当前上下文长度是 `C`。

## 不使用 KV Cache

每生成一个新 token，都重新对长度 `C` 的整个序列做前向：

```text
重新计算所有历史 token 的：
Q、K、V
MLP
Norm
Attention
```

单步注意力大致包含：

```text
O(C² × d)
```

而且所有历史 token 的线性层和 MLP 也会重复计算。

## 使用 KV Cache

只计算最新 token 的投影和 MLP：

```text
新 q、k、v：只算一次
历史 K、V：直接读取
```

单步 Attention 只需让一个新 Query 查询 `C` 个历史位置：

```text
O(C × d)
```

因此解码阶段从“对整个序列重复前向”变为“单 token 前向 + 线性扫描历史 KV”。

## 生成多个 token 时

Prompt 长度为 `P`，需要生成 `T` 个 token。

有缓存时，Attention 读取量大致是：

```text
P + (P+1) + ... + (P+T-1)
≈ T×P + T²/2
```

没有缓存时，每一步要对完整序列重新做全量 Attention：

```text
P² + (P+1)² + ... + (P+T-1)²
```

并且还会重复计算所有历史 token 的 MLP 和投影。

所以：

- 输出越长，KV Cache 越重要；
- 上下文越长，避免重算的收益越大；
- KV Cache 对 Decode 提升巨大；
- 对首次 Prefill 基本没有直接加速。

实际加速倍数不能给一个固定数字，因为还取决于模型、Prompt、输出长度、batch、硬件和 Attention Kernel。

---

# 5. KV Cache 占多少显存

近似公式：

```text
KV bytes
= batch
× sequence_length
× num_layers
× 2
× num_kv_heads
× head_dim
× bytes_per_element
```

其中 `2` 表示 K 和 V 两份缓存。

例如：

```text
层数：32
KV heads：8
head_dim：128
上下文：8192
数据类型：FP16，2 bytes
batch：1
```

缓存大小：

```text
32 × 2 × 8 × 128 × 8192 × 2
= 1 GiB
```

这只是一个请求。

如果使用普通 MHA，KV head 数从8增加到32：

```text
约 4 GiB / 请求
```

因此 GQA、MQA、MLA 的重要价值之一就是减少 KV Cache。

## 模型权重量化不等于 KV Cache 量化

例如模型权重使用 INT4，但 KV Cache 仍然使用 FP16：

```text
权重显存明显下降
KV Cache 显存没有同比下降
```

长上下文、高并发时，KV Cache 可能取代模型权重成为主要显存消费者。

---

# 6. KV Cache 的代价

## 显存占用随上下文和并发线性增长

```text
KV memory ∝ 并发数 × 上下文长度
```

因此不能只按“模型能否放进显存”估算服务容量，还要为 KV Cache、临时工作区和 CUDA Graph 预留空间。

## Decode 仍需扫描历史缓存

KV Cache 避免了重新计算 K/V，但新 Query 仍需读取历史 K/V：

```text
q_t × [K_1 ... K_t]^T
```

所以 Decode 并没有变成常数复杂度，而是随上下文长度近似线性变慢。

## 内存带宽压力

Decode 时每个请求每步只处理少量 token，计算单元不容易吃满，同时需要读取：

- 模型权重；
- 历史 KV；
- 中间激活。

因此大模型 Decode 往往偏内存带宽受限。

## 缓存可能失效

以下变化通常会导致不能复用：

- Token 序列不同；
- System Prompt 有一个 token 不同；
- 模型版本不同；
- LoRA Adapter 不同；
- RoPE 或模型配置不同；
- 多模态输入不同；
- 缓存已经被驱逐；
- 权重发生更新。

Prefix Cache 必须基于 token 和完整模型语义身份，而不能只比较原始文本看起来是否相同。

# 7. 吞吐与延迟看哪些指标

至少分开看四个指标。

## TTFT：Time to First Token

```text
请求到达
→ 排队
→ Tokenize
→ Prefill
→ 第一个 token
```

它主要受到：

- 排队；
- Prompt 长度；
- Prefill batch；
- Prefix Cache 命中；
- Chunked Prefill；
- CPU Tokenizer；

影响。

## ITL：Inter-Token Latency

相邻输出 token 之间的时间：

```text
token 1 ---- token 2 ---- token 3
        ITL        ITL
```

它主要受到：

- Decode batch 大小；
- KV Cache 长度；
- GPU 带宽；
- 调度等待；
- Prefill 是否抢占 GPU；
- Preemption；

影响。

## TPOT

平均每个输出 token 的生成时间，和 ITL 接近但统计定义可能不同。

## E2E Latency

从请求到达直到生成完成：

```text
E2E ≈ 排队 + TTFT + 输出 token 数 × TPOT
```

## Throughput

通常看：

```text
总输出 tokens / second
成功 requests / second
```

高吞吐不一定意味着用户体验好。把大量请求放进一个 batch，GPU 利用率会上升，但每个请求可能等得更久。

vLLM 官方直接暴露 TTFT、ITL、请求排队时间、Prefill/Decode 时间和 Preemption 等指标，应按 p50/p95/p99 分别监控，而不是只看平均 tokens/s。[vLLM Production Metrics](https://docs.vllm.ai/en/latest/usage/metrics/)

---

# 8. 我怎么权衡吞吐与延迟

## 在线聊天：优先 TTFT 和 ITL

我会：

- 对并发做 admission control；
- 限制单请求最大 Prompt 和输出长度；
- 开启流式输出；
- 优先调度 Decode；
- 使用 Chunked Prefill，避免长 Prompt 长时间阻塞已有 Decode；
- 对超长请求使用独立队列；
- 给交互请求设置 p95 TTFT、ITL SLO；
- 避免 KV Cache 接近100%导致频繁 Preemption。

允许牺牲一部分峰值吞吐，换取稳定的交互延迟。

## 离线批处理：优先吞吐

例如批量摘要、数据标注、Embedding 后处理，可以：

- 增大 batch；
- 增大 `max_num_batched_tokens`；
- 允许更长排队；
- 使用较大并发；
- 按长度分桶；
- 减少 padding；
- 只看整体 tokens/s 和单位成本。

## 混合负载

交互聊天与离线批处理不应完全共用同一调度策略。

更稳妥的是：

```text
在线交互池：
低排队、低 ITL、严格限制长度

离线批处理池：
大 batch、高吞吐、允许等待

超长上下文池：
单独容量和超时策略
```

否则一个10万 token 的 Prompt 可能显著恶化其他短请求的 TTFT 或 ITL。

# 9. Chunked Prefill 如何影响权衡

Prefill 通常计算密集，Decode 通常带宽受限。把两者适当混合可以提高 GPU 利用率。

Chunked Prefill 将长 Prompt 拆成若干块：

```text
长 Prompt Prefill
→ chunk 1
→ 插入 Decode
→ chunk 2
→ 插入 Decode
→ ...
```

vLLM V1 在支持时默认启用 Chunked Prefill，并优先调度 Decode。当前官方调优建议是：

- 较小的 `max_num_batched_tokens`：通常改善 ITL；
- 较大的值：通常改善 TTFT和吞吐；
- 必须用真实负载压测确定拐点。

这是调度权衡，不是“越大越快”。[vLLM Optimization and Tuning](https://docs.vllm.ai/en/latest/configuration/optimization/)

# 10. PagedAttention 解决什么问题

传统方式为每个请求预留一块连续 KV 内存：

```text
请求 A：[------------------------]
请求 B：[-------------]
请求 C：[--------------------------------]
```

但请求长度不可预测，会产生：

- 预留过多；
- 内部碎片；
- 请求结束后留下不规则空洞；
- 很难扩展连续空间；
- 多个采样分支重复保存相同前缀。

PagedAttention 将 KV Cache 切成固定 token 数的 Block：

```text
逻辑请求 A：
Block 7 → Block 21 → Block 3

物理显存：
[Block 3][Block 7][Block 9][Block 21]...
```

逻辑上连续的序列，物理上不必连续。每个请求维护自己的 Block Table。

它类似操作系统分页：

```text
Token      ≈ 字节
KV Block   ≈ 内存页
Block Table ≈ 页表
Request    ≈ 进程
```

PagedAttention 的原始论文报告，在当时对比系统和测试负载下，vLLM 在相近延迟下获得了约 `2–4×` 吞吐提升；这是系统级历史结果，不应当当成所有现代模型、硬件和版本上的固定倍数。[PagedAttention 论文](https://arxiv.org/abs/2309.06180)

## 它带来的收益

- 按需分配 KV Block；
- 减少外部碎片；
- 只有最后一个 Block 可能有少量内部浪费；
- 请求可动态增长；
- 更容易容纳更多并发序列；
- Beam Search、Parallel Sampling 可以共享前缀 Block；
- 配合连续批处理动态加入、移除请求。

## 它不解决的事情

PagedAttention 不会：

- 减少每个 token 理论上需要存储的 K/V 数量；
- 自动压缩 KV 数据类型；
- 改变模型输出；
- 消除长上下文 Attention 的线性读取；
- 让首次独有 Prompt 的 Prefill 变快；
- 解决模型权重读取的带宽瓶颈。

它主要是**内存管理和调度优化**，不是模型结构层面的 KV 压缩。

---

# 11. vLLM 需要重点注意什么

## 1. KV Cache 容量和 Preemption

如果同时运行的请求需要的 KV Block 超过容量，vLLM 会 Preempt 请求，之后重新计算其 KV Cache。

这会导致：

- TPOT/ITL 突然变差；
- E2E 延迟尾部增大；
- GPU 做重复 Prefill；
- 吞吐可能下降。

应监控：

```text
GPU KV Cache usage
request_num_preemptions
queue time
TTFT / ITL p95、p99
```

出现频繁 Preemption 时，可以：

- 降低并发；
- 减少 `max_num_seqs`；
- 限制最大上下文和输出长度；
- 增加可用于 KV 的显存；
- 使用更多 GPU；
- 使用 GQA/MQA 模型；
- 评估 KV Cache 低精度；
- 对长请求单独调度。

## 2. `max_num_batched_tokens`

它不是越大越好：

```text
较小
→ Decode 更容易及时调度
→ ITL 通常更好

较大
→ Prefill 更集中
→ TTFT和吞吐可能更好
→ 可能影响正在生成的请求
```

必须基于 Prompt 长度和输出长度分布压测。

## 3. `max_num_seqs`

增加它可以提高并发和吞吐，但也会：

- 增加 KV Cache 压力；
- 增加单步 Decode batch；
- 可能恶化单请求 ITL；
- 更容易触发 Preemption；
- 增加部分 runner/CUDA Graph 资源。

在线服务应按 SLO 定值，不应只追求最高 tokens/s。

## 4. Prefix Caching 只加速重复前缀

Automatic Prefix Caching 适合：

- 大量请求共享长 System Prompt；
- 多轮对话重复携带完整历史；
- 同一长文档被多次问答；
- 相同 few-shot 示例被反复使用。

它通常不会加速：

- 每个 Prompt 都完全不同；
- 只有短公共前缀；
- 主要成本在长输出 Decode；
- 缓存频繁被驱逐。

vLLM 使用按 Block 哈希的前缀缓存，而且只缓存完整 Block；缓存键还要考虑 LoRA、多模态输入等额外身份。[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/design/prefix_caching/)

## 5. 多租户安全

Prefix Cache 命中会改变 TTFT，可能形成时间侧信道：攻击者通过延迟差异猜测另一个租户是否使用过某段前缀。

当前 vLLM 支持通过 `cache_salt` 限制缓存复用范围；但官方明确说明，同一 vLLM 进程并不提供完整租户隔离，强隔离仍应通过独立实例或部署边界实现。[vLLM Security](https://docs.vllm.ai/en/latest/usage/security/)

实践中：

- 单租户：可以最大化共享；
- 组织内共享：每个组织使用随机 salt；
- 严格跨租户隔离：独立 vLLM 实例；
- 不要使用可预测用户名作为 salt；
- 非加密哈希要评估碰撞和隐私风险。

## 6. Block 大小不是单向优化

较小 Block：

- 最后一个 Block 浪费更少；
- 分配更细；
- Block Table 更大；
- 管理和内核寻址开销可能增加。

较大 Block：

- 元数据更少；
- 访问可能更规则；
- 短序列和尾部浪费更多；
- Prefix Cache 只能按完整 Block 命中，复用粒度更粗。

默认值通常是合理起点，除非有真实压测证据，不建议只凭直觉修改。

## 7. KV Cache 低精度要单独验证

降低 KV 精度可以扩大并发，但需要检查：

- 长上下文质量；
- 数学和代码；
- 多轮对话一致性；
- 不同层是否敏感；
- Attention backend 是否真正支持；
- 量化、反量化是否引入额外延迟。

权重量化后的精度结论不能直接推断 KV Cache 量化也安全。

## 8. 长上下文声明不等于高并发能力

模型支持128K上下文，只表示单请求理论上能处理这种长度，不表示：

- 多个128K请求能同时运行；
- TTFT可接受；
- KV Cache放得下；
- 长上下文质量没有退化；
- Prefix Cache一定会命中。

要用目标并发和真实长度分布测容量。

# 12. 我的实际调优流程

## 第一步：建立真实负载分布

至少记录：

```text
Prompt token：p50 / p95 / p99
Output token：p50 / p95 / p99
并发到达率
共享前缀比例
长对话比例
可接受 TTFT / ITL / E2E
```

## 第二步：估算 KV 容量

用模型的：

```text
num_layers
num_kv_heads
head_dim
kv_dtype
```

估算单 token、单请求和目标并发的 KV 占用。

## 第三步：分别压测 Prefill 和 Decode

需要至少四类 workload：

```text
短输入 + 短输出
短输入 + 长输出
长输入 + 短输出
长输入 + 长输出
```

只用一种固定长度压测很容易得出错误结论。

## 第四步：调度参数扫描

逐组调整：

```text
max_num_batched_tokens
max_num_seqs
最大上下文
最大输出 token
Prefix Cache
KV dtype
Tensor Parallel
```

每次记录：

```text
TTFT p50/p95/p99
ITL p50/p95/p99
E2E
输出 tokens/s
Preemption 次数
KV Cache 使用率
失败率
```

## 第五步：按 SLO 选配置

在线业务：

```text
先满足 TTFT、ITL、错误率
再在约束内最大化吞吐
```

离线业务：


最终要记住三点：

1. **KV Cache 的核心收益在 Decode，不在首次 Prefill。**
2. **PagedAttention 的核心收益是提高 KV 显存利用率和并发，不是减少模型本身的 Attention 计算。**
3. **吞吐和延迟必须用 TTFT、ITL、E2E、Preemption 以及真实长度分布一起衡量；只看 tokens/s 很容易把线上体验调坏。**
