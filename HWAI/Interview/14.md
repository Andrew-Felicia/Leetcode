训练过程中 loss 突然上升你怎么定位？从数据、优化器、学习率计划到实现细节说步骤。


我会按“**先保现场 → 判断现象类型 → 固定复现 → 从输入到参数更新逐段排查**”处理，而不是一上来就把学习率调小。

## 1. 先判断是哪一种“突然上升”

先同时看：

- 当前 batch loss；
- 平滑后的训练 loss；
- 验证 loss；
- 学习率；
- 梯度范数；
- 参数范数；
- AMP loss scale；
- 各个 loss 分项。

不同形态通常指向不同原因：

| 现象 | 优先怀疑 |
|---|---|
| 单个 step 突然升高，随后恢复 | 困难样本、坏数据、极端长度、增强过强 |
| 上升后一直不恢复 | 学习率跳变、优化器状态丢失、参数爆炸、数据分布切换 |
| 周期性上升 | 特定数据 shard、周期性 LR、验证模式错误 |
| 恢复 checkpoint 后立刻上升 | 优化器或 scheduler 状态没恢复 |
| Loss 变成 NaN/Inf | 数值溢出、非法输入、除零、空 mask |
| 训练 loss 正常，验证 loss 上升 | 过拟合、分布差异、验证流程问题 |
| 所有 GPU 同时异常 | 学习率、模型或公共数据问题 |
| 只有某个 rank 异常 | 分布式数据、坏样本、通信或设备问题 |

训练 loss 短暂波动是正常的。真正异常的是：

- 明显超过历史波动范围；
- 梯度、参数同时异常；
- 持续不恢复；
- 每次在同一位置复现；
- 出现 NaN/Inf。

---

# 2. 先保留故障现场

不要立即覆盖 checkpoint。至少保存：

```text
异常前一个 checkpoint
模型参数
优化器状态
scheduler 状态
AMP GradScaler 状态
全局 step 和 epoch
随机数状态
当前 batch 的样本 ID
数据 shard 和 rank
学习率
梯度范数
```

如果能记录样本 ID，就能回答最关键的问题：

> 这个异常是由特定 batch 触发，还是由训练状态触发？

不建议直接把异常 batch 永久跳过。跳过可以作为定位实验，但可能掩盖数据或实现问题。

---

# 3. 固定复现

从异常前的 checkpoint 重新运行，并尽量固定：

- 随机种子；
- DataLoader 顺序；
- 数据增强随机数；
- Dropout 随机数；
- 分布式 sampler；
- 当前 batch；
- 梯度累积位置。

然后观察：

### 每次在相同 batch 复现

优先查：

- 数据；
- 标签；
- mask；
- 特殊样本；
- 数值范围；
- loss 实现。

### 相同 checkpoint、相同 batch 也不能复现

优先查：

- 非确定性算子；
- 多卡同步；
- 异步数据加载；
- 混合精度；
- 未保存的训练状态；
- 随机增强。

### 换任何 batch 都会爆

优先查：

- 学习率或 scheduler；
- 优化器状态；
- 参数已经异常；
- checkpoint 恢复；
- 数值精度。

---

# 4. 第一层：检查数据与标签

我会把异常 batch 单独导出，检查原始数据、预处理后数据和标签。

## 数值输入

检查：

```text
min / max / mean / std
NaN / Inf 数量
零值比例
缺失率
序列长度或图像尺寸
是否超出正常业务范围
```

典型问题：

- 除零或对负数取对数；
- 归一化标准差为 0；
- 传感器异常值；
- 图像解码损坏；
- 空文本或超长文本；
- 数据类型转换溢出；
- 新数据源单位变化，例如“元”变成“分”。

尤其要检查预处理前后：

```text
原始金额：100 元
新数据源：10000 分
```

业务含义相同，但如果单位没有统一，模型看到的尺度会突然扩大100倍。

## 标签

检查：

- 分类标签是否在 `[0, num_classes-1]`；
- one-hot 是否正确；
- 回归标签是否有极端值；
- 分割 mask 是否出现非法类别；
- 忽略标签是否正确设置；
- 语言模型 label 是否正确右移；
- Padding 是否被计入 loss；
- 正负样本定义是否在中途变化。

常见语言模型错误：

```text
输入：  A B C D
目标：  B C D E
```

如果 label shift 错一位，loss 可能明显变化。

## Batch 组成

检查异常 batch 是否包含：

- 极端长序列；
- 罕见类别；
- 全是正样本或负样本；
- 空目标；
- 超多目标框；
- 特殊语言；
- 新的数据 shard；
- 过强数据增强。

如果使用动态 batch 或按 token 数组 batch，要看实际 token 数，而不是只看样本数。

## 数据分布切换

如果训练数据分阶段加载：

```text
通用数据
→ 代码数据
→ 数学数据
```

切换时 loss 跳高可能是正常分布变化。此时应分别记录各数据源的 loss，而不是只看混合总 loss。

# 5. 第二层：检查 Loss 本身

不要只记录总 loss，要记录各分项：

```text
total_loss
classification_loss
box_loss
mask_loss
auxiliary_loss
regularization_loss
```

如果总 loss 上升，要先知道是哪一项造成的。

## Mean 与 Sum

最常见实现错误之一：

```text
以前：对 batch 求 mean
现在：对 batch 求 sum
```

当 batch size、序列长度或有效 token 数变化时，loss 会突然改变尺度。

对于带 mask 的 token loss，通常应计算：

```text
loss = 有效 token 的 loss 总和 / 有效 token 数
```

需要防止：

```text
有效 token 数 = 0
```

否则会发生除零或 NaN。

## Loss 权重

多任务训练中检查权重是否突然变化：

```text
total_loss =
1.0 * classification_loss
+ 5.0 * box_loss
+ 2.0 * mask_loss
```

常见问题：

- warmup 后辅助 loss 权重突然放大；
- 配置读取错误；
- 动态权重没有 detach；
- 某个分项量纲变化；
- 正负样本归一化方式改变。

## 数值稳定实现

应该优先使用稳定版本：

- `CrossEntropyLoss`，不要手写 `softmax + log`；
- `BCEWithLogitsLoss`，不要先 sigmoid 再取 log；
- 使用 `logsumexp`；
- 分母加入合理 epsilon；
- 对概率取 log 前避免精确的 0；
- 避免直接计算特别大的指数。

错误示例：

```python
loss = -torch.log(torch.softmax(logits, dim=-1)[target])
```

更稳定的是直接使用：

```python
loss = torch.nn.functional.cross_entropy(logits, target)
```

# 6. 第三层：检查学习率和 Scheduler

我会记录每个 parameter group 的实际学习率，而不是只看配置文件里的初始值：

```python
for group in optimizer.param_groups:
    print(group["lr"])
```

重点检查：

## Scheduler 调用频率

某些 scheduler 按 step 更新，某些按 epoch 更新。

常见错误：

```text
本应每个 epoch 调一次
却每个 batch 调一次
```

或者相反，导致学习率变化速度完全错误。

## Warmup 边界

检查：

- 第一个 step 是否除以 0；
- warmup 结束时是否发生跳变；
- global step 是否从 0/1 开始错误；
- 恢复训练后 warmup 是否重新开始；
- scheduler 是否比 optimizer 多走或少走一步。

## Cosine Restart / Cyclic LR

如果 loss 周期性跳高，要检查学习率是否发生 restart：

```text
LR 降低
→ 突然恢复到较大值
→ loss 同步跳高
```

这可能是设计行为，也可能是配置错误。

## Batch Size 和学习率联动

如果改变：

- 单卡 batch size；
- GPU 数量；
- 梯度累积步数；
- 有效 token 数；

有效 batch size 就会变化：

```text
effective_batch
= per_device_batch
× world_size
× gradient_accumulation_steps
```

学习率若按 batch size 线性缩放，也必须同步调整。

## 不同参数组

检查是否有某组参数学习率异常：

```text
Backbone：1e-5
Task head：1e-3
```

如果误把 Backbone 也设成 `1e-3`，预训练特征可能迅速被破坏。

---

# 7. 第四层：检查优化器状态

## Checkpoint 是否完整恢复

恢复训练必须考虑：

```text
model.state_dict()
optimizer.state_dict()
scheduler.state_dict()
GradScaler.state_dict()
global_step
```

只恢复模型参数、不恢复 Adam 状态，会丢失：

- 一阶动量；
- 二阶动量；
- step 计数；
- 自适应学习率历史。

恢复后第一次更新可能与之前完全不同。

## Adam / AdamW 参数

检查：

- `betas`；
- `eps`；
- `weight_decay`；
- 参数组；
- 是否误用 Adam 的 L2 与 AdamW 的 decoupled weight decay；
- Norm 和 bias 是否不该施加 weight decay；
- 是否有参数重复出现在多个 parameter group。

过小的 `eps` 在低精度训练中可能增加数值风险。

## 参数冻结和解冻

如果训练中途解冻 Backbone，大量新参数突然开始更新，loss 可能跳高。

解冻时通常要考虑：

- 更小学习率；
- 分阶段 warmup；
- 是否把新参数加入 optimizer；
- optimizer state 是否正确初始化；
- BatchNorm 统计量是否一起变化。

## 梯度清零

PyTorch 默认累加梯度。检查是否正确执行：

```python
optimizer.zero_grad(set_to_none=True)
```

如果漏掉，梯度会在多个 step 间无意累积。

同时确认梯度累积代码是否正确：

```python
loss = loss / accumulation_steps
loss.backward()
```

每累计指定步数后才：

```python
optimizer.step()
optimizer.zero_grad()
```

常见错误：

- 忘记把 loss 除以累积步数；
- 多执行一次 `optimizer.step()`；
- 累积边界错位；
- 最后不足一个完整累积周期的 batch 处理错误。

# 8. 第五层：检查梯度

我会记录：

- 全局梯度范数；
- 各层梯度范数；
- 最大绝对梯度；
- NaN/Inf；
- 参数范数；
- 参数更新量与参数量之比。

关键量：

```text
update_ratio = ||ΔW|| / (||W|| + eps)
```

如果某层的更新量突然接近或超过参数本身，通常说明更新过激。

## 梯度爆炸

典型信号：

```text
loss 上升
→ gradient norm 急剧变大
→ 参数范数变大
→ 出现 Inf/NaN
```

可以记录：

```python
total_norm = torch.nn.utils.clip_grad_norm_(
    model.parameters(),
    max_norm
)
```

返回值是裁剪前的总范数，可用于日志。

但梯度裁剪只是一种保护措施。还要查明是：

- 学习率过高；
- 极端 batch；
- loss 缩放错误；
- 长序列；
- 不稳定激活；
- 归一化错误；
- 优化器状态异常。

## 梯度消失或断开

如果 loss 上升但前层梯度突然接近 0，检查：

- 意外 `.detach()`；
- `torch.no_grad()` 范围过大；
- 使用 `.item()` 后重新构造 loss；
- 不可导操作；
- ReLU 大量死亡；
- mask 把所有位置清零；
- 参数 `requires_grad=False`；
- 优化器没有包含相关参数。

---

# 9. 第六层：检查混合精度

FP16 的数值范围有限，常见问题是梯度溢出。

应监控：

- GradScaler 的 scale；
- 是否频繁跳过 optimizer step；
- loss 是否在放大前已是 Inf；
- 梯度在 unscale 前还是后检查；
- 某些敏感算子是否被错误地强制成 FP16。

正确顺序通常是：

```python
with autocast():
    loss = model_and_loss(...)

scaler.scale(loss).backward()

scaler.unscale_(optimizer)
clip_grad_norm_(model.parameters(), max_norm)

scaler.step(optimizer)
scaler.update()
```

梯度裁剪应该在 `unscale_` 之后进行，否则裁剪的是被放大的梯度。

## FP16 与 BF16

如果硬件支持，BF16 通常具有与 FP32 相同的指数范围，更不容易溢出；但有效精度较低，仍可能有数值误差。

定位实验可以依次尝试：

1. 关闭 AMP，用 FP32 重跑异常 batch；
2. FP16 改为 BF16；
3. 将 Softmax、归一化和 Loss 保持在 FP32；
4. 检查自定义 CUDA 算子。

如果 FP32 正常而 FP16 异常，基本可以把范围缩小到数值精度和 AMP 实现。

# 10. 第七层：检查激活和参数

对各模块记录：

```text
输出 min/max/mean/std
NaN/Inf 数量
激活范数
梯度范数
```

可以通过 forward hook 和 backward hook 定位第一处异常层。

关键不是找“哪一层出现 NaN”，而是找：

> **沿前向或反向顺序，第一处从正常变成异常的位置。**

例如：

```text
Layer 20 输出正常
Layer 21 Attention logits 极大
Layer 21 Softmax 出现 NaN
Layer 22 开始全部 NaN
```

根因更可能在 Layer 21，而不是后面所有显示 NaN 的层。

重点检查：

- Attention logits 是否过大；
- LayerNorm/RMSNorm 分母；
- 方差是否接近 0；
- 激活是否持续放大；
- 权重初始化；
- Residual 分支缩放；
- Embedding 中是否存在异常行；
- 自定义归一化实现；
- In-place 操作。

# 11. 第八层：检查模型状态与实现细节

## `train()` 与 `eval()`

检查是否错误切换：

```python
model.train()
model.eval()
```

它会影响：

- Dropout；
- BatchNorm；
- 某些随机层；
- 部分量化或缓存逻辑。

常见问题是验证结束后忘记切回：

```python
model.eval()
validate()
# 忘记 model.train()
```

## BatchNorm

Batch size 很小或数据分布突然变化时，BatchNorm 统计量可能不稳定。

检查：

- 每卡 batch size；
- 多卡是否使用 SyncBatchNorm；
- running mean/variance；
- 冻结 Backbone 时 BN 是否仍更新；
- 恢复 checkpoint 时统计量是否加载。

小 batch 场景可以考虑 GroupNorm、LayerNorm，或冻结 BN 统计量。

## In-place 操作

例如：

```python
x += residual
```

可能破坏反向传播需要保存的中间值，尤其在复杂分支和自定义 autograd 中。

框架有时会直接报错，但某些自定义实现可能产生更隐蔽的问题。

## 自定义梯度

如果使用自定义 `autograd.Function` 或 CUDA kernel：

- 用双精度小输入做 gradient check；
- 与纯 PyTorch 参考实现比较；
- 检查边界条件；
- 检查 backward 是否漏加某个分支；
- 检查广播维度和 reduction。

---

# 12. 第九层：检查分布式训练

多 GPU 下还要额外排查：

## 某个 Rank 的坏数据

一个 rank 出现 NaN 后，All-Reduce 可能把 NaN 传播给所有 GPU。

因此每个 rank 分别记录：

```text
loss
样本 ID
梯度范数
NaN/Inf
数据 shard
```

不要只记录 rank 0。

## Loss 和梯度缩放

确认：

- DDP 是否已经对梯度求平均；
- 代码是否又手动除了一次 `world_size`；
- loss 是 sum 还是 mean；
- 梯度累积时 `no_sync()` 边界是否正确；
- 有效 batch size 是否改变。

重复平均会让梯度过小，漏平均或错误求和则可能导致梯度过大。

## 数据采样

检查 DistributedSampler：

- 是否调用 `set_epoch(epoch)`；
- 不同 rank 是否意外读到完全相同数据；
- shard 是否均衡；
- 最后一个 batch 是否异常小；
- 数据断点恢复后 sampler 位置是否一致。

## 通信与硬件

排查：

- NCCL 错误；
- GPU ECC/Xid 错误；
- 某个设备温度或频率异常；
- 自定义通信压缩；
- 低精度梯度 All-Reduce；
- 参数是否在所有 rank 保持一致。

可以在关键 step 对不同 rank 的参数 checksum 或范数做比较。

# 13. 用消融快速缩小范围

如果问题仍不明确，我会从异常前 checkpoint 做以下对照实验：

```text
A：原始配置
B：固定异常 batch
C：关闭数据增强
D：关闭 AMP，使用 FP32
E：单 GPU
F：固定较小学习率
G：换成简单优化器
H：关闭新增 loss 或模块
```

根据结果缩小范围：

| 实验结果 | 更可能的原因 |
|---|---|
| 关闭增强后正常 | 数据增强或标注同步错误 |
| FP32 正常，FP16 异常 | 数值溢出、AMP、自定义算子 |
| 单卡正常，多卡异常 | DDP、数据 shard、通信 |
| 换 batch 后正常 | 数据或极端样本 |
| 固定小 LR 后正常 | Scheduler 或更新幅度 |
| 不恢复 optimizer 后行为不同 | 优化器状态 |
| 关闭新模块后正常 | 新模块前向、反向或初始化 |

# 14. 一个实用的排查顺序

我会严格按这个顺序执行：

1. 确认是单点波动、持续上升还是 NaN。
2. 保存异常前 checkpoint、训练状态和样本 ID。
3. 从异常前 checkpoint 固定数据顺序复现。
4. 检查异常 batch 的原始数据、标签、mask 和增强。
5. 拆开记录每个 loss 分项及其归一化分母。
6. 记录每个参数组的真实学习率。
7. 检查 scheduler 调用时机和恢复状态。
8. 检查 optimizer、GradScaler、global step 是否完整恢复。
9. 记录全局和逐层梯度范数、参数范数、更新比例。
10. 关闭 AMP，用 FP32 重跑异常 batch。
11. 单 GPU 重跑，排除分布式问题。
12. 用 hook 找到第一处非有限或异常放大的层。
13. 对新增代码和配置做二分消融。
14. 修复后从异常前 checkpoint 重跑，并补回归测试。

# 15. 定位后常见修复

| 原因 | 修复 |
|---|---|
| 坏样本或非法标签 | 修复数据管道、增加输入校验 |
| 极端长尾样本 | 合理变换、截断、分桶或稳定 loss |
| 学习率过高 | 降低 LR、增加 warmup、修复 scheduler |
| 恢复时状态丢失 | 同时恢复 optimizer、scheduler、scaler、step |
| 梯度爆炸 | 查根因，并增加 clipping 作为保护 |
| FP16 溢出 | BF16、动态 loss scaling、敏感算子用 FP32 |
| Loss reduction 错误 | 明确 sum/mean 和有效样本分母 |
| 梯度累积错误 | 统一 loss 缩放、step 和 zero_grad 边界 |
| BatchNorm 不稳定 | 增大 batch、SyncBN、冻结 BN 或换 GroupNorm |
| DDP 某 rank 异常 | 逐 rank 记录数据和梯度，修复 sampler |
| 转阶段数据变化 | 分数据源记录 loss，必要时重新 warmup |
| 自定义算子错误 | gradient check，与参考实现逐项对比 |

最关键的经验是：

> **先找到“第一处异常”以及“是否绑定特定 batch”，再决定调参。**

直接降低学习率或加梯度裁剪可能暂时让 loss 不爆，但如果根因是错误标签、除零、checkpoint 状态丢失或 DDP 缩放错误，只会把真正的问题藏起来。
