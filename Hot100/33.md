This is the classic **Search in Rotated Sorted Array** problem. Since the requirement is an $O(\log n)$ runtime, a standard linear search won't cut it. We need to adapt **Binary Search**.

The core trick here is realizing that if you divide a rotated sorted array in half, **at least one of the two halves will always be strictly sorted**.

---

### The Strategy

Instead of looking for the target immediately, we use our middle pointer (`mid`) to find which side of the array is normally sorted:

1. **Check which half is sorted:**
* If `nums[left] <= nums[mid]`, then the **left half** is continuously sorted.
* Otherwise, the **right half** must be continuously sorted.


2. **Check if the target lies within the sorted half:**
* Once you identify the sorted half, you can easily check if the `target` falls within its boundaries using simple comparisons.
* If it does, narrow your search to that half.
* If it doesn't, the target *must* be in the other (rotated) half.



---

### Python 3 Implementation

```python
class Solution:
    def search(self, nums: list[int], target: int) -> int:
        left, right = 0, len(nums) - 1
        
        while left <= right:
            mid = (left + right) // len(nums)  # Or left + (right - left) // 2
            
            if nums[mid] == target:
                return mid
            
            # Condition 1: Check if the left half is strictly sorted
            if nums[left] <= nums[mid]:
                # Check if the target lies within this sorted left half
                if nums[left] <= target < nums[mid]:
                    right = mid - 1  # Search left
                else:
                    left = mid + 1   # Search right
                    
            # Condition 2: The right half must be strictly sorted
            else:
                # Check if the target lies within this sorted right half
                if nums[mid] < target <= nums[right]:
                    left = mid + 1   # Search right
                else:
                    right = mid - 1  # Search left
                    
        return -1

```

### C++ Implementation

```cpp
#include <vector>

class Solution {
public:
    int search(std::vector<int>& nums, int target) {
        int left = 0;
        int right = nums.size() - 1;
        
        while (left <= right) {
            int mid = left + (right - left) / 2;
            
            if (nums[mid] == target) {
                return mid;
            }
            
            // Left half is sorted
            if (nums[left] <= nums[mid]) {
                if (nums[left] <= target && target < nums[mid]) {
                    right = mid - 1; // Search left
                } else {
                    left = mid + 1;  // Search right
                }
            } 
            // Right half is sorted
            else {
                if (nums[mid] < target && target <= nums[right]) {
                    left = mid + 1;  // Search right
                } else {
                    right = mid - 1; // Search left
                }
            }
        }
        
        return -1;
    }
};

```

### Complexity Analysis

* **Time Complexity:** $O(\log n)$ because we discard half of the search space at each iteration, exactly like standard binary search.
* **Space Complexity:** $O(1)$ as we only use a few tracking variables (`left`, `right`, `mid`).


That is completely okay! This problem is notoriously tricky when you first encounter it because it breaks our usual assumption about how binary search works. Let’s strip away the code entirely and look at exactly how this works under the hood.

---

## 1. The Core Secret of a Rotated Array

In a normal binary search, the entire array is perfectly sorted from smallest to largest. If you pick any middle element, everything to its left is smaller, and everything to its right is larger.

When an array is **rotated**, that neat pattern breaks. For example:
`[4, 5, 6, 7, 0, 1, 2]`

However, a beautiful mathematical property emerges here:

> If you cut a rotated sorted array exactly in half, **one of those two halves will always be a perfectly normal, non-rotated sorted line of numbers.** The other half will contain the "pivot" point where the numbers drop back down to zero.

Let's test this rule on our example array `[4, 5, 6, 7, 0, 1, 2]`.
The middle element is **7** (index 3). This splits our array into two halves:

* **Left Half:** `[4, 5, 6, 7]`
* **Right Half:** `[7, 0, 1, 2]`

Look closely at them. The left half goes perfectly up from 4 to 7. It is **perfectly sorted**. The right half goes from 7 down to 0 and back up to 2. It is **broken (rotated)**.

Because the left half is normal, we can confidently ask a simple question: *"Is our target between 4 and 7?"* If yes, we search the left. If no, it *must* be in the broken right half.

---

## 2. A Step-by-Step Walkthrough (Tracking the Target: 0)

Let's trace exactly what the computer does if we are searching for the target **0** in the array `[4, 5, 6, 7, 0, 1, 2]`.

We start with two pointers marking the boundaries of where we are looking:

* `left` is at index 0 (value **4**)
* `right` is at index 6 (value **2**)

### Round 1:

1. **Find the Middle:** The middle between index 0 and 6 is index 3. The value at `nums[mid]` is **7**.
2. **Is it our target?** Does 7 equal 0? No. Moving on.
3. **Which half is the "Normal" one?**
We compare the `left` value (**4**) with our `mid` value (**7**).
Since 4 is less than or equal to 7 (`4 <= 7`), we know for an absolute fact that the **left half is perfectly sorted**.
4. **Is the target inside this normal half?**
Our normal half goes from 4 to 7. Is our target (0) between 4 and 7? **No.**
Since it cannot possibly be in the left half, we throw the left half away! We update our search boundary by moving `left` to `mid + 1` (index 4).

### Round 2:

Now we are only looking at the remaining right side: `[0, 1, 2]`

* `left` is now at index 4 (value **0**)
* `right` is still at index 6 (value **2**)

1. **Find the Middle:** The middle between index 4 and 6 is index 5. The value at `nums[mid]` is **1**.
2. **Is it our target?** Does 1 equal 0? No.
3. **Which half is the "Normal" one?**
We compare our new `left` value (**0**) with our new `mid` value (**1**).
Since 0 is less than or equal to 1 (`0 <= 1`), the **left side of this new section is perfectly sorted** (`[0, 1]`).
4. **Is the target inside this normal half?**
Our normal section goes from 0 to 1. Is our target (0) between 0 and 1? **Yes!** (In fact, it is exactly 0).
Because it is in this range, we throw away the right side. We update our boundary by moving `right` to `mid - 1` (index 4).

### Round 3:

Now both `left` and `right` are at index 4.

1. **Find the Middle:** The middle is index 4. The value at `nums[mid]` is **0**.
2. **Is it our target?** Does 0 equal 0? **Yes!**
3. We return the index **4**. We found it!

---

## 3. Why the Code is Structured the Way It Is

If you look back at the code logic, it follows a strict nested "If/Else" pattern to handle this specific thought process:

* **IF `nums[left] <= nums[mid]**` $\rightarrow$ This means the left side is normal.
* *Inside here:* If the target falls between `nums[left]` and `nums[mid]`, look left. Otherwise, look right.


* **ELSE** $\rightarrow$ If the left side wasn't normal, then by default, the **right side must be the normal one**.
* *Inside here:* If the target falls between `nums[mid]` and `nums[right]`, look right. Otherwise, look left.



By always finding the "normal" half first, we can use standard logic to decide whether to jump left or right, shrinking our search space by half every single time. That is what keeps it lightning-fast at $O(\log n)$ speed!

### The Integer Overflow Detail (C++)

While `mid = (left + right) // 2` is perfectly correct and safe in Python (because Python handles infinitely large integers automatically), you will often see it written differently in languages like C++, Java, or Go:

```cpp
int mid = left + (right - left) / 2;

```

Even though both formulas are mathematically identical, programmers use the second one to prevent a sneaky issue called **integer overflow**.

Here is why:

* In languages like C++, standard integers (`int`) have a maximum storage capacity (usually up to $2,147,483,647$).
* If you are searching through a truly massive array where `left` and `right` are both very large numbers, adding them together (`left + right`) might exceed that maximum limit.
* When an integer exceeds its maximum limit, it "overflows" and flips into a negative number, crashing your index calculation.

By using `left + (right - left) / 2`, you subtract the numbers first (which results in a small value), divide that small value by 2, and add it back to `left`. This guarantees the numbers never cross the danger zone.

But for Python? `(left + right) // 2` works flawlessly every single time!
