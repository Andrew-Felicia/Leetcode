This problem is a bit trickier than a standard tree traversal because the paths **don't have to start at the root**, and they **don't have to end at a leaf**. They just have to go downwards.

If you try to check every possible starting node and calculate all paths down from it, you end up with an inefficient $O(N^2)$ or $O(N \log N)$ solution.

Instead, we can solve this in **$O(N)$ time** by borrowing a brilliant concept from array problems: **Prefix Sums** combined with a **Hash Map**.

---

### The Core Concept: Prefix Sums

A **prefix sum** is the running total of all node values from the absolute root down to your current node.

Imagine you are walking down a single branch of the tree:
`Root (10) -> Node (5) -> Node (3)`

* At `10`: Current running sum = `10`
* At `5`: Current running sum = `10 + 5 = 15`
* At `3`: Current running sum = `15 + 3 = 18`

Now, let's say our `targetSum` is `8`. When we are standing at the node `3` (where our total running sum is `18`), we want to know: *Is there a sub-path right above us that sums to 8?*

Mathematically, if we can find an older prefix sum up the chain that equals `Current Sum - targetSum`, then the path *between* that old node and our current node **must** sum exactly to `targetSum`.

$$18 (\text{Current}) - 8 (\text{Target}) = 10$$

Do we have a prefix sum of `10` earlier in our path? Yes! It happened at the root. That means the path *after* the root down to our current node (`5 -> 3`) sums exactly to `8`.

---

### Using a Hash Map to Track History

As we travel deeper into the tree using Depth-First Search (DFS), we keep track of how many times each prefix sum has occurred in a hash map (`prefix_sums`).

1. **Set the Base Case:** Initialization.
Initialize the hash map with `{0: 1}`. This represents an imaginary path of sum `0` before the root, which is essential if a valid path starts exactly at the root.


2. **Update the Running Sum:** Traversal.
As you step onto a node, add its value to your `current_sum`.


3. **Look for Completing Paths:** Check Map.
Check if `current_sum - targetSum` exists in your hash map. If it does, add its frequency to your total path count.


4. **Clean Up on Return:** Backtracking.
Before the recursive function returns (as you move back up to a parent node), decrement the count of `current_sum` in the map. This prevents nodes from a completely different branch of the tree from interfering with the current path.


---

### Python 3 Implementation

```python
from collections import defaultdict

# Definition for a binary tree node.
class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

class Solution:
    def pathSum(self, root: TreeNode | None, targetSum: int) -> int:
        # Map to store: [prefix_sum : number of times it occurred in current path]
        prefix_sums = defaultdict(int)
        # Base case: a prefix sum of 0 is seen exactly 1 time (before the root)
        prefix_sums[0] = 1
        
        def dfs(node, current_sum):
            if not node:
                return 0
            
            # 1. Update the running prefix sum
            current_sum += node.val
            
            # 2. Check if there's an older prefix sum that satisfies: 
            #    current_sum - old_prefix_sum = targetSum
            #    which rewrites to: old_prefix_sum = current_sum - targetSum
            count = prefix_sums[current_sum - targetSum]
            
            # 3. Add the current prefix sum to the map so deeper child nodes can use it
            prefix_sums[current_sum] += 1
            
            # 4. Continue DFS down the left and right subtrees
            count += dfs(node.left, current_sum)
            count += dfs(node.right, current_sum)
            
            # 5. Backtrack: Remove the current sum from the map as we move back up the tree
            prefix_sums[current_sum] -= 1
            
            return count

        return dfs(root, 0)

```

### Complexity Analysis

* **Time Complexity:** $O(N)$, where $N$ is the number of nodes in the tree. We visit each node exactly once, and hash map insertions and lookups take $O(1)$ time.
* **Space Complexity:** $O(N)$ in the worst-case scenario (a completely linear, skewed tree) to store the prefix sums in the hash map and handle the recursion stack. For a balanced tree, the space complexity would be $O(\log N)$.



Let's break this down piece by piece. The combination of tree traversal and prefix sums can feel a bit abstract, so we will use a concrete example and trace exactly how the data moves.

---

### 1. The Core Trick: The "Sub-segment" Math

Imagine you are measuring a long piece of wood.

* You mark a spot at **10 inches** from the start.
* You keep pulling the tape measure until you reach **18 inches**.
* If someone asks you, "How long is the piece *between* your 10-inch mark and your 18-inch mark?", you subtract them: $18 - 10 = 8\text{ inches}$.

The Prefix Sum algorithm works exactly like that tape measure. As we travel down a single vertical branch from the root, we keep track of the **running total** (the prefix sum).

If we are standing at a node where our running total is `18`, and our `targetSum` is `8`, we ask our history map: *"Hey, did we ever see a running total of `10` ($18 - 8$) higher up on this exact path?"*

If the answer is yes, it means the nodes *between* that old spot and our current spot add up **exactly to 8**.

---

### 2. Tracing an Example Step-by-Step

Let's look at a simple straight-line branch from Example 1:

```
    10  (Root)
   /
  5
 /
3       (Target Sum = 8)

```

We will track two things as we go down:

1. `current_sum`: The running total.
2. `prefix_sums`: A map that remembers how many times we've seen a specific sum on our current path. We start it with `{0: 1}` because before we even look at the root, our sum is 0.

#### Step A: At Node `10`

* **Calculate:** `current_sum = 0 + 10 = 10`
* **Check:** Look for `current_sum - targetSum` $\rightarrow$ `10 - 8 = 2`. Is `2` in our map? No. (No paths found yet).
* **Record:** Add our current sum to the map.
* **Map State:** `{0: 1, 10: 1}`

#### Step B: Move down to Node `5`

* **Calculate:** `current_sum = 10 + 5 = 15`
* **Check:** Look for `current_sum - targetSum` $\rightarrow$ `15 - 8 = 7`. Is `7` in our map? No.
* **Record:** Add our current sum to the map.
* **Map State:** `{0: 1, 10: 1, 15: 1}`

#### Step C: Move down to Node `3`

* **Calculate:** `current_sum = 15 + 3 = 18`
* **Check:** Look for `current_sum - targetSum` $\rightarrow$ `18 - 8 = 10`. Is `10` in our map? **Yes!**
* **Result:** `prefix_sums[10]` is `1`. This means there is **1** valid path ending at our current node. (That path is just the node `5` and node `3`, because $5 + 3 = 8$).
* **Record:** Add our current sum to the map.
* **Map State:** `{0: 1, 10: 1, 15: 1, 18: 1}`

---

### 3. The Magic of "Backtracking" (The Clean-up)

This is the part that trips most people up. A tree has many branches. What happens when we finish checking the left side of the tree and want to move over to the right side?

Let’s expand our tree slightly:

```
      10
     /  \
    5   -3
   /
  3

```

When our code finishes checking the branch `10 -> 5 -> 3`, the recursion finishes with node `3` and pops back up to node `5`, and then back to `10`. Now, it prepares to dive down into the right child, node `-3`.

If we don't clean up our map, the map will still contain the numbers `15` and `18` from the left branch! If we left them there, node `-3` might mistakenly look at them and think they are part of its own history, which would completely break our math.

To prevent this, right before our function leaves a node to go back up, it runs this line:

```python
prefix_sums[current_sum] -= 1

```

It **erases** its own footprint from the history map. By the time the code switches over to look at node `-3`, the map only contains the history of nodes directly above it (which is just the root `10`).

---

### 4. Why do we need `prefix_sums[0] = 1`?

Imagine a path starts exactly at the root. For example, if the root itself is `8` and our target is `8`.

* At the root, `current_sum = 8`.
* We check for `current_sum - targetSum` $\rightarrow$ `8 - 8 = 0`.
* If we didn't put `0: 1` in our map at the very beginning, the code wouldn't find `0`, and it would miss the fact that the root itself is a valid path! Setting `0: 1` handles paths that start from the very top.
