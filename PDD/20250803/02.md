## How `sys.stdin` works

`sys.stdin` is a file-like object representing your program's **standard input stream** — normally your keyboard, but it can be redirected to come from a file (`< input.txt`) or from another program's output (`prog1 | prog2`).

Key things about it:
- It's a **stream**, not a list — you consume it once, in order, from start to end.
- `sys.stdin.read()` reads *everything* available until it hits **EOF** (end-of-file). For a file, EOF happens naturally when the file ends. For an interactive terminal, EOF only happens when you manually signal it (`Ctrl+D` on Linux/macOS, `Ctrl+Z`+`Enter` on Windows) — which is exactly the "won't stop" behavior you saw earlier.
- Alternatives: `sys.stdin.readline()` reads one line at a time; iterating `for line in sys.stdin:` reads line by line lazily. I used `.read()` because competitive-programming judges usually feed a whole file at once, and reading everything up front then parsing with `.split()` is simpler and faster than parsing line-by-line when the token counts per line vary.

```python

```
Builds the adjacency list for the directed graph: `adj[i]` will hold the list of nodes reachable *directly* from node `i` (i.e., nodes `i` can activate). Starts as `n` empty lists — one per user.

```python

            xi, yi, ri = pts[i]
            ri2 = ri * ri
```
For each user `i`, unpack their coordinates and radius, and precompute `ri²` once outside the inner loop (avoids recomputing `ri*ri` for every `j`, a small optimization).

```python
            for j in range(n):
                if i == j:
                    continue
```
Compare `i` against every other user `j`; skip self-comparison.

```python
                xj, yj, _ = pts[j]
```
Unpack `j`'s coordinates. The `_` throws away `j`'s radius — irrelevant here, since the edge `i → j` only depends on *`i`'s* radius (that's the key asymmetry in this problem: `i` activating `j` only requires `j` to be within `i`'s reach, not vice versa).

```python
                dx = xi - xj
                dy = yi - yj
                if dx * dx + dy * dy <= ri2:
                    adj[i].append(j)
```
Computes squared Euclidean distance `dx² + dy²` and compares it against `ri²` — mathematically equivalent to `sqrt(dx²+dy²) ≤ ri`, but avoids floating-point `sqrt` entirely (which could introduce rounding errors at the boundary, e.g. when distance exactly equals the radius). If within range, add the directed edge `i → j`.

Now try every user `s` as the starting (manually activated) node, and track the best result seen.

```python

```
Standard DFS/BFS setup: a `visited` array to avoid revisiting nodes, a `stack` (list used as a stack, via `.pop()`/`.append()`) seeded with the start node, and a running `count` of activated users (starting at 1, since `s` itself is activated).

```python
            while stack:
                u = stack.pop()
                for v in adj[u]:
                    if not visited[v]:
                        visited[v] = True
                        count += 1
                        stack.append(v)
```
Classic DFS: pop a node `u` off the stack, look at everyone `u` can directly activate (`adj[u]`), and for each unvisited neighbor `v`, mark it visited, increment the count, and push it onto the stack to explore its neighbors later. This continues until the stack is empty — meaning we've found everyone reachable from `s`.

```python

```
After exhausting reachability from `s`, update the best total-activated-count seen so far across all starting choices.


Store this test case's answer (as a string, ready for joining/printing) after trying every possible start.

After all test cases are done, join every result with newlines and print them in a single call — again, batching output rather than calling `print()` in a loop, which is a common performance habit in competitive programming.
