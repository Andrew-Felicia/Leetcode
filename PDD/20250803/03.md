Let's break this down into two layers: the **algorithmic idea** (why this approach is correct) and the **code mechanics** (line by line).

## The problem, restated

You have `n` LEDs with brightness values. You can only **increase** brightness (never decrease), one unit at a time. You want to pick some interior position `i` and make the sequence strictly increase up to `i`, then strictly decrease after it — using the fewest total `+1` operations possible.

## Why brute force is too slow

You could try every peak position, and for each one, simulate raising values to enforce strict monotonicity — but recomputing that from scratch for every peak is `O(n)` per peak, `O(n²)` overall. With `n` up to `100000`, that's too slow. The trick is to **precompute once**, then answer every peak position in `O(1)`.

## The key insight: split the problem in two independent halves

Notice something important: whether position `j` is on the "increasing" side just depends on making `a[0], a[1], ..., a[j]` strictly increasing — it **doesn't matter yet where the peak ends up being**, as long as `j` is somewhere on the left side of it. So I can precompute, once, for the *entire array*, "what's the minimum value position `j` would need if it were part of a strictly-increasing prefix?" That's independent of the eventual peak location.

Same logic applies symmetrically from the right for the decreasing side.

### Step 1 — `leftreq`: minimum value needed if increasing from the left

```python
leftreq = [0] * n
leftreq[0] = a[0]
for j in range(1, n):
    leftreq[j] = max(a[j], leftreq[j - 1] + 1)
```

This is a classic greedy pattern: walk left to right. At each position, the value must be **at least one more** than the position before it (`leftreq[j-1] + 1`) to keep things strictly increasing — but we never decrease `a[j]` below its original value, so we take whichever is bigger: the original value, or the minimum forced by the previous position.

Example: `a = [2, 2, 2]`
- `leftreq[0] = 2` (unchanged)
- `leftreq[1] = max(2, 2+1) = 3`
- `leftreq[2] = max(2, 3+1) = 4`

So if the increasing run extended all the way to index 2, it'd need to become `[2, 3, 4]`.

### Step 2 — `rightreq`: same idea, mirrored, from the right

```python
rightreq = [0] * n
rightreq[n - 1] = a[n - 1]
for j in range(n - 2, -1, -1):
    rightreq[j] = max(a[j], rightreq[j + 1] + 1)
```

Walking right to left, each position must be at least one more than the position *after* it, to keep things strictly decreasing looking forward.

For `a = [2, 2, 2]`:
- `rightreq[2] = 2`
- `rightreq[1] = max(2, 2+1) = 3`
- `rightreq[0] = max(2, 3+1) = 4`

### Step 3 — prefix/suffix cost sums

```python
prefix[j] = prefix[j-1] + (leftreq[j] - a[j])
suffix[j] = suffix[j+1] + (rightreq[j] - a[j])
```

These just track: "if I enforce the increasing (or decreasing) requirement up through index `j`, how many total `+1` operations does that cost?" Since `leftreq[j] - a[j]` is exactly how much position `j` needs to be bumped up, summing these gives a running total — a classic prefix-sum trick so we can query "total cost from 0 to `j`" in `O(1)` instead of re-summing every time.

### Step 4 — evaluate every possible peak position

```python
for i in range(1, n - 1):
    peak_value = max(leftreq[i], rightreq[i])
    cost = prefix[i - 1] + suffix[i + 1] + (peak_value - a[i])
```

Here's the subtle part. Position `i` is special: it's shared by *both* the increasing constraint (it's the last element of the "up" run) and the decreasing constraint (it's the first element of the "down" run). So its final value must be big enough to satisfy **both** — hence `max(leftreq[i], rightreq[i])`.

The total cost for choosing peak `i` breaks into three independent pieces:
- **Left side** (`prefix[i-1]`): cost to make everything strictly increasing from index `0` up to `i-1`. This doesn't involve the peak itself, so we use the prefix sum up to (but not including) `i`.
- **Right side** (`suffix[i+1]`): cost to make everything strictly decreasing from `i+1` to the end. Same idea, mirrored.
- **The peak itself** (`peak_value - a[i]`): how much `a[i]` needs to be bumped to satisfy whichever of the two constraints is stricter.

Why is it valid to compute these three pieces independently, rather than worrying they interact? Because `leftreq[i-1]` only cares about being less than whatever `a[i]` *becomes* — and since we're setting `a[i]` to the max of both requirements (which is always `≥ leftreq[i] > leftreq[i-1]`), the increasing property at the boundary is automatically preserved. Same argument applies on the right. So the three pieces truly don't interfere with each other, and we can just add them up.

Finally, we try every valid interior position `i` (from index `1` to `n-2`, since the peak can't be the very first or last LED) and keep the cheapest one.

## Worked example

For `a = [2, 2, 2]`, the only valid peak is index `1` (the middle element, since `n=3` only has one interior position):
- `prefix[0] = leftreq[0] - a[0] = 2 - 2 = 0`
- `suffix[2] = rightreq[2] - a[2] = 2 - 2 = 0`
- `peak_value = max(leftreq[1], rightreq[1]) = max(3, 3) = 3`
- `cost = 0 + 0 + (3 - 2) = 1`

Matches the expected answer — you only need to bump the middle LED once, turning `[2,2,2]` into `[2,3,2]`.

## Why this runs fast enough

Every step here — building `leftreq`, `rightreq`, `prefix`, `suffix`, and scanning all peak candidates — is a single `O(n)` pass. Total time is `O(n)`, easily handling `n` up to `100000` well within typical time limits.
