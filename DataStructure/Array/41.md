Your code is a very natural and logical attempt, but it is actually **not** $O(n)$ time. That is exactly why LeetCode is throwing a **Time Limit Exceeded (TLE)** error.

Let's break down why your code is slower than it looks, and then we will look at a mind-blowing trick called **Cyclic Sort** to achieve a true $O(n)$ time and $O(1)$ space solution.

---

## Why your code is NOT $O(n)$

There are two hidden performance traps in your current implementation:

### 1. `positive.contains(i)` inside a loop is $O(n^2)$

Your loop runs from `1` up to `maxValue`. Inside that loop, you call `positive.contains(i)`.
To check if a number exists in an `ArrayList`, Java has to scan the list from the beginning to the end, which takes $O(n)$ steps *every single time*. Running an $O(n)$ scan inside a loop that runs up to $n$ times results in a **quadratic time complexity of $O(n^2)$**. Given LeetCode's constraint of $10^5$ elements, an $O(n^2)$ algorithm requires roughly 10 billion operations, causing it to time out.

### 2. Space Complexity is $O(n)$

You are creating a brand new `ArrayList` called `positive` to store all the positive numbers. This breaks the strict interview constraint of using **$O(1)$ auxiliary space**.

---

## The $O(1)$ Space Secret: Cyclic Sort (The "Bucket" Trick)

For an array of length $n$, the smallest missing positive integer **must** fall in the range of `1` to `n + 1`.

Instead of tracking values elsewhere, we can use the input array itself as a hash map! Our goal is to rearrange the array *in-place* so that every positive number `x` sits at the index `x - 1`.

* The number `1` should go to index `0`
* The number `2` should go to index `1`
* The number `3` should go to index `2`, and so on.

Any numbers that are negative, zero, or too big (greater than $n$) can just be ignored or overwritten because they cannot be our missing answer.

---

## 🛠️ The True $O(n)$ Time and $O(1)$ Space Code

Here is how you implement this in pure Java using basic array manipulation:

```java
class Solution {
    public int firstMissingPositive(int[] nums) {
        int n = nums.length;

        // Step 1: Cyclic Sort - Place each number in its correct "bucket"
        for (int i = 0; i < n; i++) {
            // While the current number is in the valid range (1 to n)
            // AND it's not already sitting in its correct index (nums[i] != nums[nums[i] - 1])
            while (nums[i] > 0 && nums[i] <= n && nums[i] != nums[nums[i] - 1]) {
                // Swap nums[i] to its correct target index: nums[i] - 1
                int targetIndex = nums[i] - 1;
                int temp = nums[i];
                nums[i] = nums[targetIndex];
                nums[targetIndex] = temp;
            }
        }

        // Step 2: Find the first index that doesn't match its expected value
        for (int i = 0; i < n; i++) {
            if (nums[i] != i + 1) {
                return i + 1; // Found the missing positive!
            }
        }

        // Step 3: If all spots are perfectly filled [1, 2, 3, ..., n], 
        // then the missing positive is the next integer.
        return n + 1;
    }
}

```

---

## Why does the `while` loop inside the `for` loop stay $O(n)$?

It looks like nested loops, which usually means $O(n^2)$, but look closer:
Every time a swap happens inside the `while` loop, at least **one number lands permanently in its final correct home**. Since there are only $n$ elements, you can perform at most $n$ successful swaps across the *entire* execution of the program.

Therefore, the total time spent swapping elements is $O(n)$, and the space complexity is **$O(1)$** because we only used a couple of basic primitive integers (`targetIndex`, `temp`) and modified the input array completely in-place.
